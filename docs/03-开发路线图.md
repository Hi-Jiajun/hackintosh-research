# 开发路线图：Windows 上的新黑苹果（reims-vgpu 生态）

> 面向 Hi-Jiajun/reims-vgpu fork 的开发计划。阶段 1-5 的目标机是 Windows；
> 本工作区（Linux）负责研究、交叉验证、Rust 侧开发与测试。
> 每个阶段遵循上游 AGENTS.md 的验证纪律：测试定义完成、fail log 双通道、n≥3、
> 不在无测量时下结论。

## 阶段 0：工作区就绪（已完成）

- `reference/`：六个仓库的 README 存档；
- `repos/`：fork-reims-vgpu、upstream-reims-vgpu、qemu-reims-vgpu（blobless 浅克隆，
  取 blob 用 `git show FETCH_HEAD:<path>` 按需拉取）、metal2vulkan、27on86、asahi-kvm；
- `docs/`：本系列调研文档。
- 注意：fork 目前与 upstream master 完全同步；qemu 子模块未在 fork 内初始化
  （`git submodule update --init vendor/qemu` 需要时执行）。

## 阶段 1：Windows 构建打通（目标：qemu-system-x86_64.exe 认得 reims-vgpu-pci）

1. 目标机安装：MSYS2（mingw64 工具链 + 依赖：glib2、pixman、zlib、SDL2/GTK、ninja、
   meson、pkg-config）、Rust（`x86_64-pc-windows-gnu` target）、Vulkan SDK、
   LLVM（llvm-dis）、SPIRV-Tools（spirv-val）、Python。
2. 修改 qemu fork `hw/display/meson.build`：为 `host_os == 'windows'` 增加
   Rust 系统库臂（Unix 的 -lm/-ldl/-lpthread 在 mingw 不存在/不同）。
3. 用 `--no-default-features --features backend-vulkan` 构建 Rust staticlib
   （backend-metal 默认特性在非 macOS 是编译错误，属预期）。
4. 编译 QEMU fork（x86_64-softmmu + aarch64-softmmu 两个目标都试），修 shim 的
   Windows 编译问题（预期：PCI 壳的 mmap 打包视图需要条件编译或禁用）。
5. 验收：`qemu-system-x86_64.exe -device help` 出现 reims-vgpu-pci；
   `qemu-system-aarch64.exe -device help` 出现 reims-vgpu-mmio。
6. 交叉验证：同一棵树在 Linux 上也编译通过、`cargo test -- --test-threads=1` 全绿。

## 阶段 2：host-window 的 Windows 臂（目标：Windows 上弹出 Reims 窗口）

1. `backend/vulkan/engine/context.rs` 的实例扩展选择加
   `#[cfg(target_os = "windows")]` → `ash::khr::win32_surface::NAME`；
2. 跑 `host_window_smoke` example（host-window feature）；
3. `runtime/host.rs` alloc_block 增加 Windows 臂（VirtualAlloc 预留+提交，或普通堆
   + 拷贝）；先把打包视图做成"拷贝填充"，正确性优先；
4. 验收：无客户机也能弹窗渲染测试图案；fail log 无 typed decline。

## 阶段 3：路径 A 冒烟（目标：Windows 上 WHPX 加速的 macOS 13 图形桌面）

1. 客户机预置：Linux 机器上按 OSX-KVM 流程装好 macOS 13（post-Setup-Assistant、
   开远程登录），把磁盘/OpenCore/OVMF 导入 reims rails（`--device vmware-svga`
   的测试 boot 先验证客户机本身在 Windows QEMU 上能起）；
2. WHPX 验证：`-accel whpx` 引导到桌面（先用 vmware-svga，隔离变量）；
   若 WHPX 有 macOS 兼容问题（见可行性分析 2.3 #7），记录并退 TCG；
3. 换 `--device reims-vgpu-pci` + Vulkan 后端：桌面出现、截图对比、读 fail log；
4. 验证矩阵（AGENTS.md）：import on/off 对照 boot、像素对照、panic 检查、
   present_hz/offered_hz 成对读数；
5. 收尾：Windows 版 boot 脚本（PowerShell 或 msys2 bash）提交到 fork。

## 阶段 4：路径 B（目标：Windows 上 TCG 引导 arm64 macOS 13 headless）

1. 从真 Mac 获取 AVPBooter.vmapple2.bin + macosvm 预置的 vmapple bundle（合规红线：
   不进库、不上传）；
2. 参考 27on86 的实验记录（repos/27on86/docs/experiments/）与
   qemu fork 的 steelbrain/macos-arm64-fixes 分支，拆 vmapple.c 的 HVF 假设，
   在 Windows 上以 TCG 实例化；
3. 先 headless（串口 + SSH，27on86 的 M2 判据）；再挂 reims-vgpu-mmio 看极慢速 GUI；
4. 期望管理：这是开发/研究环境，不是日用。

## 阶段 5：性能 rails（目标：把拷贝路径逐步换成导入路径）

1. 在目标机 ICD 上验证 `VK_EXT_external_memory_host`（读 vk_caps 行）；
2. 若有：跑通 host-pointer 导入（context.rs 的 linux 臂外再加 windows 臂，Windows
   导入不需要 fd）；对比 import on/off 的 present_hz（AGENTS.md 有基线：off ≈ 1/2 帧率）；
3. 打包视图 Windows 实现（消除散页资源的 gather/copy）；
4. WHPX dirty-log 实测（i386 有 dirty tracking 实现；验证 reims 脏页 witness 可用）。

## 阶段 6：上游贡献与 fork 维护

- **分支策略**：fork 的 master 严格跟随 upstream；Windows 工作放
  `windows-*` 分支；阶段性 PR 回 upstream（项目欢迎 Windows 相关工作——README 明说
  "making more host/guest combinations reliable" 是欢迎方向）。
- 跟踪 upstream 的 `steelbrain/macos-arm64-fixes` 分支（fork 目前没有）。
- **metal2vulkan**：从路径 D 的翻译缺陷开始贡献（bugs/ 目录的包装格式见 AGENTS.md）；
- 加入项目 Discord（README 里有链接），配合 rail/measurement 文化汇报结果
  （"哪个 rail 出的数字"必须写明）。
- 每次开工前 `git ls-remote` 检查 metal2vulkan pin（AGENTS.md 专门警告过 pin 落后）。

## 阶段 D（随时可做）：纯 Windows 上的开发

- metal2vulkan：llvm-dis + spirv-val（Windows 官方二进制）→ `cargo test`、
  `cargo clippy -- -D warnings`、`cargo doc` 全绿；
- reims-vgpu-wire 解码：fixture 测试不需要虚拟机；
- 本工作区 Linux 侧可跑全部 Rust 测试与 QEMU Linux 构建作为 CI 前的交叉验证。

## 合规红线（任何时候）

固件、IPSW、恢复镜像、VM 磁盘、VM 身份、日志、OpenCore/OVMF 运行时永不入库；
不传播 macOS 或绕过 Apple 恢复签名；遵守 macOS 许可的适用限制（自担风险）。
