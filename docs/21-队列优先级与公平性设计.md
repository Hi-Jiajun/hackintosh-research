# 队列优先级与公平性设计（2026-09-13）

> 承接 `docs/09`（canonical Metal semantic path）与 `docs/14` §8 第 4 个开放问题。
> 本文定义 provider 调度侧（宿主侧）的队列优先级契约与选择算法。第一版只做**契约 + 算法 +
> 单测**，不把优先级接进 trace/wire（`MCC1`）与对象 API 的公开面——那会引入新的线格式问题，
> 留给后续轮次。

## 1. 问题

`crates/metal-api-vulkan/src/lib.rs` 的 `select_queue` 目前只有一个维度：**最少在途提交数 +
轮询游标打散同分**。它保证负载均衡，但不表达任何优先级：

1. 一旦所有队列都在途，选择退化为纯轮询，"短延迟任务"无法越过"长任务"，出现队头阻塞；
2. reims 线（`docs/09` Gate 2/3）会有多个 guest 命令队列共享同一个宿主 device，
   宿主需要一个**可解释、可复算**的排队策略，而不是隐式的 FIFO；
3. README 的 "Open design work" 明确列着 `priority/fairness in queue scheduling` 未完成。

本机限制：Lavapipe 只有 `queues=1 families=1`，多队列策略无法在本机观察；真机是 RTX 5060
`queues=8 families=2`（证据 `evidence/compute-family-queues-4181b08-2026-09-09/`：
`PASS provider_object_concurrent_enqueue submissions=8 queues=8 families=2 distinct=8
host_enqueue=concurrent`）。

## 2. 为什么不改创建期的队列优先级

Vulkan 的队列优先级是**设备创建期参数**，运行期不可改：

- `VkDeviceQueueCreateInfo::pQueuePriorities`（以及 `VK_KHR_global_priority` /
  `VK_EXT_global_priority` 的 `VkDeviceQueueGlobalPriorityCreateInfo*`）只在 `vkCreateDevice`
  时生效；`vkGetDeviceQueue`/`vkGetDeviceQueue2` 只是取回创建时的声明值。想要"另一个优先级"
  就必须销毁设备重建——而设备的生命周期已经绑定了 `docs/15` 的共享 per-allocation device
  buffer 与 `docs/13` 的有界放弃账本，重建等于丢掉全部在途工作与预约状态。
- 创建期优先级只能表达"这个队列比那个队列重要"，无法表达 guest 在一次提交里的意图，
  也无法跨进程/重启复算；它对宿主自己的可观测面（trace、证据）是不可见的。
- Vulkan 规范把队列优先级定义为 hint，实现可以宽松处理，`vkQueueSubmit` 之间没有执行级
  抢占保证，因此即便改了创建期优先级也不解决"已经在 GPU 上跑的工作"。这与 `docs/04`
  的性能与原生度结论一致：控制点应该在宿主调度，而不是依赖驱动的时间片。

结论：走**调度侧加权 + 无饥饿**路径。契约类型放 core（backend-neutral），Vulkan 与 native
两个 provider 共用同一语义，且是**无状态纯函数**：输入只有"每队列在途计数 + 每队列优先级 +
单调游标"，输出被选中的队列下标。这样它可单测、可跨进程重放、可在证据里复算，不需要 WFQ
那种每队列虚拟时间（虚拟时间在跨进程/重启时无法保持一致）。

## 3. 契约类型

`crates/metal-api-core/src/provider.rs`：

| 类型 | 作用 |
|---|---|
| `QueuePriority { Low, Default, High }` | 调度侧优先级档位；`Default` 是 `Default` 值，也是今天所有队列的档位 |
| `QueueSchedulingPolicy` | 权重窗口：`low_weight`/`medium_weight`/`high_weight`（默认 1/2/4），私有字段 + 构造函数，权重 0 被夹到 1 |
| `select_queue_with_priority(in_flight, priorities, round_robin_start, policy) -> usize` | 纯函数选择算法 |

三个硬不变量（写进文档注释与单测）：

1. **空闲/最少在途优先**：保留现有 `select_queue` 的核心语义，档位只在"同负载"的候选集合里
   起作用，高优先级的忙队列不会越过低优先级的空闲队列；
2. **同负载下按窗口提名档位优先**：高档位在窗口里拿到更多槽位；
3. **无饥饿**：每一档在每个窗口内都至少有一个槽位，"高优先级连续被选中"的次数有显式上限。

## 4. 算法与公式

窗口长度为三档权重之和，槽位按高档在前排列：

```text
W       = w_low + w_medium + w_high            = 1 + 2 + 4 = 7
schedule= [H, H, H, H, D, D, L]                （每窗口 7 个槽位）
L       = w_high                               = 4      ← 高优先级连续选中上限
```

于是：

- **加权份额**：三档都有队列可用时，长期份额 `High:Default:Low = 4:2:1`；
- **无饥饿**：`w_* ≥ 1` 保证每档每窗口至少 1 个槽位；低优先级最坏等待 6 次选择（≤ 1 个窗口）；
- **上限公式**：`high_priority_streak_limit() = w_high`，因为窗口把高档槽位排在最前，
  所以"连续命中上限"就等于高档权重本身，调用方不需要再推导窗口。

选择过程（`select_queue_with_priority`，O(n)、无分配、无锁、无状态）：

1. 取**最少在途**的队列作为候选集合（全空闲或全同负载时即全体）；
2. 在候选集合上折叠出"目标档位"，回退顺序为：**被提名档位 → 低于提名的最高档 →
   高于提名的最近档**。第二步的用意是：当被提名档位在当前候选中缺席时，把槽位让给更低档而
   不是更贪婪的高档。只有 `High` 与 `Low` 两类队列时，窗口会得到 `H H H H L L L`
   （`D` 的槽位让给 `L`），即份额 4:3 而不是 4:2:1；
3. 从 `round_robin_start mod n` 开始**环形扫描**，返回第一个"最少在途且属于目标档位"的队列。

**退化等价性**：当所有队列同档（今天 provider 的真实情形）时，第 3 步就是现有
`select_queue` 的"从游标开始取最小负载"，新算法因此是现算法的严格泛化，而不是并行的一套
语义。Vulkan crate 的单测对 `n ≤ 3`、每队列负载 `0..=2`、游标 `0..6` 做了**全枚举比对**
（`queue_priority_policy_reduces_to_select_queue_on_one_tier`）。

## 5. 与 `docs/14` §8 第 4 个开放问题的关系

`docs/14` §8 的第 4 条是："与 queue priority/公平性的交互：range hazard 是否作为调度的
第二维度"。本文只回答**第一维度**：

- 第一维度（优先级/公平性）不需要任何 per-queue 状态就能表达，且与 `docs/14` 的 range
  hazard 正交——算法只依赖"候选集合 + 目标档位"，**候选集合如何被过滤是调用方的事**。
  将来把 hazard 升级成第二维度时，只需把 hazard 冲突集合作为前置过滤，窗口公式不变；
- 反向约束必须写清：`docs/14` 的 whole-allocation 预约（同一 allocation 的命令缓冲区串行化）
  是**正确性**约束，优先级不得越过它。本文的算法天然满足这一点——它只在候选集合内部选择，
  不会把被预约挡住的队列重新拉回调度。真正开放的是"区间级 hazard 是否让同一档位的队列
  进一步排序"，本文不动。

## 6. 真机验证方案（RTX 5060，`queues=8 families=2`）

现有观测面（都是公开 API，先例见 `evidence/compute-family-queues-4181b08-2026-09-09/`）：

- `VulkanExecutor::queue_submission_counts()`：每个设备队列的累计成功提交数；
- `VulkanExecutor::set_enqueue_probe_for_test(probe)`：在持有该队列宿主入队锁时回调被选中的
  队列下标（`provider_object_concurrent_enqueue` 的 `host_enqueue=concurrent` 就是它给出的）。

接线完成后（本轮的后续轮次）执行：

1. 在 `provider-smoke` 增加探针场景：8 个队列标记为 1×`High` + 1×`Default` + 6×`Low`，
   连续提交 `N = 70`（10 个窗口）个互不依赖的命令缓冲区；
2. 断言 `queue_submission_counts()` 的分布符合窗口：三档齐全时高档合计/中档合计/低档合计
   ≈ `4:2:1`（允许因"被提名档位缺席"的让位规则带来的偏差，偏差值由第 4 节的回退顺序决定）；
3. 用 `set_enqueue_probe_for_test` 记录实际被选下标序列，断言"高档连续命中 ≤ `w_high`（4）"
   且"每个 7 次窗口内低档至少 1 次"——这是无饥饿的直接证据；
4. Lavapipe（本机 `queues=1 families=1`）只能验证退化路径：单队列时计数恒等于 1 个队列、
   且与 `select_queue` 逐点一致（现有 `SKIP provider_object_concurrent_enqueue
   reason=single_queue queues=1` 是同一原因）。

边界：这只证明**宿主侧选择与提交分布**符合契约，不证明 GPU 侧执行顺序或抢占——Vulkan 队列
优先级是 hint，`vkQueueSubmit` 之间没有执行级抢占保证（见 §2）。

## 8. 边界与未完成

- **未接线**：`VulkanContext::select_queue` 的现网路径不变，per-queue 优先级还没有进入
  trace/wire 与对象 API；优先级是进程内概念，不跨进程、不跨重启保持；
- **无抢占**：已在 GPU 上执行的工作不会被高优先级取代，算法只影响后续选择的分布；
- **与 hazard 的第二维度交互**未做（§5）；
- **真机分布观测未执行**（§6）：需要先完成 wire 侧接线，本机 Lavapipe 只有 1 个队列；
- 第一版只有三档权重（1/2/4），没有 `realtime` 档，也没有"每队列独立的权重"；
- 未定义"优先级从哪来"：`QueuePriority` 目前只能由宿主显式传入，guest/对象 API 的映射
  （例如 `MTLCommandQueue` 的哪一属性映射到哪一档）是下一轮的设计题目。
