## 2. reims-vgpu 的主要变化

从 `747580f` 到 `69a57dd` 共 255 个提交。与 provider 计划直接相关的变化集中在
以下几类：

### 2.1 Device-owned Vulkan caches

`50a3b9d` 将 `ObjectCaches` 从进程级 Vulkan engine 状态移入每个 `DeviceState` 的
`DeviceObjectCaches`。新的公开入口形态是：

```text
execute_draw_request(&DeviceState, &DrawRequest)
execute_compute_request(&DeviceState, &ComputeRequest)
```

理由是 shader/pipeline/render-pass/sampler cache 的 key 来自 guest 声明，不能跨
guest device 生命周期共享。对我们的影响：旧的 `bd62f89` adapter 依赖无 state 的
全局入口，不能直接套到新 master；provider bridge 必须明确拿到对应的 `DeviceState`
或由 owner 提供一个独立的 off-guest device context，不能在 bridge 内私自再建一套
cache owner。当前离线 adapter 创建的 `DeviceState` 仅用于测试，cache 仍由该 state
的 reims owner 承载；生产 guest 路径应注入其真实 state。

### 2.2 Compute usage 在 admission/preflight 发布

`24a5e47`、`1fab7d6`、`9483849` 等提交让 compute shader 的资源访问/usage 在
admission 前由 preflight 依据已解析的 dispatch 发布。这样 ordering/lease model
可以在执行前知道 buffer/resource 的读写用途，而不是等到 Vulkan dispatch 才补答。

对 provider 的影响：未来 provider trace 必须携带或引用已解析的 usage/lease 合同；
不能把一次离线执行返回的 readback 当成 ordering model 的唯一事实。

### 2.3 Legacy cutover 和 dead tree 删除

`4da5e2f`、`ff97a31`、`213010b`、`a925b13`、`aa07715` 删除了旧 compute/render/
stream decoder 及其 dead register。新 master 的源码结构更接近唯一 live model，
但也意味着旧路径文件名、测试入口和文档行号不能作为新 patch 的稳定接口。

### 2.4 Engine API / layout 变化

Vulkan engine 的 compute path 改为 device-owned cache、in-place layout canonicalization
和 layout identity；`ComputeRequest`/`ComputeDispatch` 的字段大体保留，但调用者、
cache 参数和错误处理发生变化。旧接缝的 exact-thread 构造器、设备 limit 校验和
同步入口需要在新 owner 结构中重新落位，不能机械 cherry-pick。

### 2.5 Metal 侧没有现成 provider 抽象

Metal 相关文件仅有少量生命周期/接口调整；Vulkan/neutral compute 则发生了大规模
重构，但没有出现 `MetalApiProvider`、Metal-on-Vulkan facade 或统一 provider trait。
Discord 构想仍是待实现的架构目标，不是已经合入上游的功能。

## 3. 为什么旧 `bd62f89` 不能直接提交

在基于 `69a57dd` 的隔离 worktree 中尝试 cherry-pick `bd62f89`：

- `types.rs`、`context.rs`、`exec_compute.rs`、`runtime/compute_exec/vulkan.rs` 能部分
  自动合并；
- `engine/mod.rs` 因全局 cache → device-owned cache 的重构发生冲突；
- 直接保留旧入口会绕过新 `DeviceState` cache owner，违反上游刚建立的生命周期合同。

因此 `bd62f89` 只保留为“旧基线的实验提交”，不应作为对上游的 PR 直接发送。正确
做法是基于 `69a57dd` 重新设计一个最小 provider/测试接缝，并在新 owner 边界写测试。

## 4. 对 Metal API 统一目标的影响

上游更新实际上强化了目标文档中的一条原则：

```text
neutral model / device lifetime
        ↓
canonical Metal semantic execution path
        ↓
host provider (native Metal or Vulkan emulator)
```

Device-owned cache、pipeline usage preflight 和 device teardown 说明 provider 不能
成为一个脱离 guest/device 生命周期的“万能全局 executor”。后续抽象应：

1. 保留 `reims-vgpu-core`、protocol、memory、scheduler 的现有 owner；
2. 让 canonical Metal semantic path 持有 provider context/lifetime；
3. 让 native Metal 和 Vulkan provider 接收同一份已解析的 operation trace；
4. 先迁移 compute-buffer，保留 texture/render/ICB/window/scanout 的共享状态；
5. 只有 Gate 1 parity、Gate 2 canonical rail integration、Gate 3 VM E2E 都通过，
   才删除对应 direct Vulkan duplicate。
