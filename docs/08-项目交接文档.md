## 1. 项目目标

在 Windows 上跑起可用的 macOS VM（new-era hackintosh），技术栈是 steelbrain 的
reims-vgpu 生态：QEMU（WHPX 后端）+ reims-vgpu PCI 设备（Rust 解码 guest GPU
命令流 → host Vulkan 执行）。guest 不装任何第三方 GPU 驱动（只用 WhateverGreen/Lilu
配合）。

当前主线目标（按优先级）：
1. **解决 boot 慢**（冷启动 15-20 分钟且随机波动）——根因已收窄，见 §5；
2. **查清上游同步版 panic**（同步上游 101 提交后 kext 加载完必 panic）——A/B 回退
   验证进行中，见 §5；
3. **修桌面闪烁/条纹**（copying rail + dirty-rect 呈现）——根因已定位，见 §5；
4. 长期：让 WHPX 通路达到 Linux KVM 通路的可用度（boot 快、画面稳）。

## 3. 常用操作手册

### 3.1 构建 Windows QEMU（MSYS2）

```bash
# 从 WSL 调用（环境变量必须齐全）：
/mnt/c/msys64/usr/bin/bash.exe -lc 'export MSYSTEM=MINGW64 PATH=/mingw64/bin:/usr/bin:$PATH PYTHONUTF8=1 PYTHONIOENCODING=utf-8 CARGO_REGISTRIES_CRATES_IO_PROTOCOL=sparse CARGO_REGISTRIES_CRATES_IO_INDEX=sparse+https://mirrors.tuna.tsinghua.edu.cn/crates.io-index/; cd /c/hackintosh/reims-vgpu/vendor/qemu/build && ninja qemu-system-x86_64.exe'
# ninja 目标名必须带 .exe 后缀：qemu-system-x86_64.exe
# Rust 全量重建约 3-10 分钟；构建时不能有 QEMU 在跑（exe 被锁会 link 失败）
```

### 3.2 启动 VM

```bash
/mnt/c/msys64/usr/bin/bash.exe -lc 'export MSYSTEM=MINGW64 PATH=/mingw64/bin:/usr/bin:$PATH PYTHONUTF8=1 PYTHONIOENCODING=utf-8; cd /c/hackintosh/reims-vgpu && QMP_PORT=4499 GDB=1 MACHDD_DEV="nvme,serial=macos" bash vm/boot-windows.sh'
# 环境变量：RAM（默认16G）、MACHDD_DEV（默认 ide-hd,bus=sata.4；NVMe 用 nvme,serial=macos）、
# GDB=1 开 gdbstub(:1234)、REIMS_VGPU_WINDOW=on 开宿主窗口
# OpenCore 菜单默认停在 EFI 项——需要人工选 Macintosh HD 才会继续！
```

### 3.3 运行时诊断接口

- QMP：tcp 127.0.0.1:4499（python socket + json，qmp_capabilities 后逐命令；
  注意 WSL 下 127.0.0.1 可直达 Windows 服务）；`stop`/`cont` 控制运行
- gdbstub：127.0.0.1:1234（WSL 的 gdb 可连）。**WHPX 限制**：
  单步极慢、断点/continue 报 "target is running"（gdbstub 状态机问题），
  可靠用法 = QMP stop 后 gdb 读寄存器/内存（p/x、x/、monitor xp 读物理内存）
- serial：C:/hackintosh/vm/serial-windows.log（guest 的 -v serial=3 输出）
- fail log：C:/tmp/reims-vgpu-fail.log（reims 设备 typed reasons；每次 boot 前清）

### 3.4 slide 推算方法（重要）

1. QMP stop 后 gdb 读 CPU0 RIP；
2. 取 RIP 低 21 位（slide 是 0x100000 对齐），在 assets/kernel-disasm-full.txt 里找
   该偏移的所有指令边界候选；
3. 用字节序列定死（如 rep movsb 处 16 字节 f3a4c3660f1f4400004887fee9e8ffff）；
4. 双地址交叉验证（如 kernel base 0xffffff8000100000 处 89c7bc00 与 disasm 一致）。

## 4. 已解决事项（勿重复劳动）

1. **6 个 WHPX 修复**（PR #3，whpx-fixes 分支）：INIT IPI vector-0 投递、
   #PF 拦截+回注（inject_back_pf）、SYSENTER MSR、CPUID leaf4 拦截、
   TSC-deadline 隐藏、IA32_MISC_ENABLE(0x1a0) 处理。boot 崩溃链靠这套全打通，
   16 AP 可全部启动，guest 可到桌面。
2. llvm-dis/spirv-val 工具链（MSYS2 pacman 安装 mingw-w64 llvm-tools + spirv-tools）
   ——缺它时 draws_fail=56592 全黑屏。
3. fork 同步 + PR 整理（round15-16）。
4. Gemini 建议中已验证无效/排除的：RTC/HPET/TSC 假设（与观测矛盾）、
   kernel-irqchip=off（会退回更慢路径）、APFS TRIM quirk（循环早于磁盘 mount）、
   NVMe 换盘（无效果）、CR3 周期 flush（无效果，且同值写可能被 Hyper-V 优化）、
   24G 内存（无效果）。OpenCore 已设 SetApfsTrimTimeout=0 / ProvideCurrentCpuInfo=true
   / DisableRtcChecksum=true（无害保留）。

## 5. 未解决问题与证据链

### 5.1 boot 慢（最高优先）

**现象**：kdp_core 之后 15-20 分钟慢速阶段（随机波动，最短见过 ~5 分钟）。

**证据链**：
- CPU0 卡在 memcpy 核心（unslid 0xffffff8000101057 的 rep movsb），rcx 恒 0x4000
  （零进展），IF=0；目标地址每次 boot 不同（0xffffffec/94/fd/aa 等高位区）；
- walk 目标页：PML4 项存在但 PDPTE=0（映射从未建立）；
- guest 不 panic（vm_fault 返回"成功"）→ 疑走 physmap/reserved 判定分支不修页；
- Hyper-V 对 PF 不 exit 到 QEMU（ExceptionExitBitmap 里 PF 位正确、GPF 位同批设置
  且 GPF 确实 exit；PF 每次 boot 只 exit 恰好 1 次后就不再 exit）；
- 30 轮密集采样：vm_fault/pmap_enter 命中 0（handler 极快）——慢在"重试-再 fault"
  次数巨多，非 handler 慢；
- KVM 对照：同镜像无此循环（WHPX 特有）。

**候选下一步**（按可行性）：
a) QEMU 侧软件断点：whpx_vcpu_run 的 exit 处理里比对 RIP==vm_fault+slide 时打印
   寄存器——但慢速阶段零 exit，需要先解决"强制 exit"（试 InterruptWindow exit
   请求 WHvX64RegisterDeliverabilityNotifications 的 InterruptWindowExitable）；
b) 深挖"PF 只 exit 一次"：第一次 exit 前后 QEMU 做了什么（inject_back_pf 后
   Hyper-V 行为变化？）；
c) xnu 源码审查：vm_fault 对 physmap/reserved 的判定分支（assets/xnu-full/ 源码在）。

### 5.2 上游同步版 panic（次优先，阻塞"用上游新代码"）

**现象**：Windows 树同步上游（Rust c7c4183 + C shim 1c9c3aa3）后两次 boot 均在
kext 列表加载完成后 panic（stackshot + corefile，serial 无 panic 文本）。
同步前旧版可到桌面。

**A/B 回退状态（当前卡点）**：回退组合（Rust=2835b6c0 PR#57 版 + C=3aba725a PR#2
版）构建成功但 QEMU 报 'reims-vgpu-pci' is not a valid device model name——
hw_display_reims-vgpu-pci.c.obj 仅 721 字节（stub）。**待查**：hw/display/meson.build
的 shim 编译条件为什么在回退组合下生成 stub（比较上游同步版与回退版的 meson 配置
差异；可能需要重跑 configure）。

**另一条路**：直接取 guest corefile 看 panic 栈（panic 时写 guest 磁盘，
下次 boot 进系统后从 /Library/Logs/DiagnosticReports 取）。

### 5.3 闪烁/条纹（第三优先）

**现象（用户描述）**：显卡用上了、整体流畅；只有鼠标移动/拖动的地方才刷新画面；
拖动窗口时窗口四周闪烁+条纹。

**证据链**：
- fail log：qemu_map_pages_callback_failed ×552（KVM 对照 0）；失败列表全
  fragmented（type4 大 surface 2040 页 physical_runs=493）；
- Windows 无 mmap：C shim _WIN32 分支对 scattered 列表 return -1（既定行为）；
- Rust 侧 typed refusal 链路正常：contig_view_refused → type11_load_seed
  outcome=guest_pages → DeviceLocal 分配成功；
- 结论：闪烁/条纹 = copying rail 的缺陷（条纹=row-pitch/布局，闪烁=拷贝-呈现
  不同步/dirty-rect 旧帧缺失）。上游 101 提交里有两个疑似相关修复
  （guest_ram span bound、partial write took the whole frame）——被 5.2 的
  panic 挡住无法验证效果。

## 6. 硬约束与坑（血泪清单）

1. **一次只跑一个 VM**（Windows WHPX 与 WSL KVM 都要占资源）；测前清
   /tmp/reims-vgpu-fail.log 与 serial-windows.log。
2. Windows 树 vendor/qemu 无 git——**改前备份**；MSYS2 构建时不能有 QEMU 进程
   （exe 锁导致 link 失败）。
3. WHvGet 对**运行中** VP 返回 stale（上次 exit 的值）——只有 QMP stop/gdb 挂起后
   读数才准确；CR3 flush 曾因写回 stale 值把 guest 弄崩。
4. gdb 断点/单步在 WHPX 下基本不可用（target running 状态机问题 + 单步极慢）。
5. 每轮 boot 验证成本 15-20 分钟——批量收集数据，别一次只测一个假设。
6. AGENTS.md（repos/fork-reims-vgpu 内）适用：合同 checkpoint 流程、禁 commit
   第三方二进制/反汇编、kvm.c 脏改动是用户的所有物勿动勿提交、提交前走验证门。
7. Windows 树 QEMU 的 whpx-all.c 有大量临时诊断（rippoll/stall/exitseq/pf-seq/
   PF-DIAG/GPF-DIAG/WHPX-EXC-BITMAP 打印）——**不进上游 PR**，可继续用。
8. TS/工具侧小坑：模板字符串里 `${...}` 会炸，用 String.raw 或字符串拼接。
9. bash 工具偶发 "missing required property description" 假错误——重试即可。
