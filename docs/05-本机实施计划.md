## 3. 剩余路径（按序）

### 3.1 QEMU 构建验收
构建完成后：`vendor/qemu/build/qemu-system-x86_64 -device help | grep reims`
应出现 `reims-vgpu-pci`。

### 3.2 客户机预置（需要你参与，约 1-2 小时）
1. `cd repos/osx-kvm && python3 fetch-macOS-v2.py`（从 Apple 下载 macOS 13 Ventura
   恢复镜像，~1 GB；合规自担）；
2. `./OpenCore-Boot.sh` 用我们的 QEMU（KVM）启动安装器，经 WSLg 窗口交互完成安装
   （全自动 BaseSystem 流程约 30-60 分钟）；
3. 安装后：开远程登录（SSH）、关睡眠/屏保，干净关机。

### 3.3 导入 rails 并捕获快照
按 fork README：把 macos.img / OpenCore.qcow2 / OVMF_VARS-1920x1080.fd 放入
`vm/disks/rails/macos-13/snapshots/base/`（chmod 444 + 软链 current），
`vm/boot-x86.sh --rail macos-13 --capture` 后干净关机生成黄金快照。

### 3.4 冒烟 boot（正确性验证，非性能）
1. `vm/boot-x86.sh --testing --device vmware-svga --rail macos-13`（QEMU GTK 控制台）；
2. `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json vm/boot-x86.sh --testing
   --device reims-vgpu-pci --rail macos-13` + 宿主截图脚本；
3. 读 `/tmp/reims-vgpu-fail.log`（boot 前 `rm -f`），按 AGENTS.md 双通道判读。
预期：lavapipe 是 CPU 渲染，帧率低但像素正确——本阶段验证通路，不测性能。

### 3.5 Windows 原生阶段（真性能：WHPX + RTX 5060 原生 Vulkan）
见 docs/02/03：meson Windows 链接臂、win32 surface、打包视图降级、WHPX 冒烟。
可走 MSYS2 或从 WSL 交叉编译（mingw-w64 + rust gnu target）。

## 4. 已知风险与纪律

- Dozen 不可用于 reims（崩溃已复现，证据在 /tmp/reims-test.log）；lavapipe 只做开发验证；
- 每次 boot 前 `rm -f /tmp/reims-vgpu-fail.log`；boot 身份记录（rev/二进制哈希）按
  新版 AGENTS.md 执行；
- 固件/镜像/日志不进库；macOS 获取与虚拟化许可自担；
- sudo 密码不在任何文件落盘；会话结束后可自行轮换。

## 8. Windows 全速 boot 诊断：两个精确隔离的 bug（2026-08-31 凌晨）

**WHPX 本身对 macOS 客户机是工作的**：vmware-svga 控制台 boot 下 OpenCore 完成引导、
XNU 接管（`HANDOFF TO XNU`）、Apple logo 显示、SSH 应答——硬件虚拟化通路成立。

### Bug A（优先级最高）：reims-vgpu-pci 在 Windows 上卡死 OpenCore 早期初始化
- 现象：设备挂上后，OpenCore 第一条日志（`#[EB|`）都出不来；TCG 与 WHPX 复现相同
  → 与加速器无关，是设备在 Windows 上的移植缺陷；WSL/Linux（KVM）同配置正常。
- 证据：QMP `info registers` 两次采样显示客户机在 0xFEE00900（APIC ICR）活跃打转
  ——等待 AP 启动/事件，永不前进；fail log 只有 `host_window_capture_unsupported
  window_system=unknown`（Windows 上捕获 rail 不可用）。
- 头号嫌疑：x86 早期控制台 rail 依赖宿主窗口/捕获机制排空（OpenCore 首条控制台
  写入阻塞 → 永不排空）；修复方向在 `crates/reims-vgpu/src/host_window/capture/`
  与 shim 的 `reims_vgpu_qemu_console_feed` 路径，需给 Windows 一个不依赖捕获的
  排空路径（或 typed decline 让控制台直通）。

### Bug B：WHPX + XNU 引导到 Apple logo 后 VM 停止
- 现象：svga 通路下用户看到 OpenCore 选盘 → Apple logo → 无进度条，窗口标题
  QEMU(STOPPED)。
- 证据：boot 日志末行 `WHPX: Unexpected VP exit code 4`（不可恢复异常，WHPX
  停止 VP）；伴随 CPUID 警告：tsc-deadline/arat/pcid 被 WHPX 隐藏——XNU 期待的
  定时器特性缺失是头号嫌疑。
- 方向：QEMU whpx 后端的 CPU 特性暴露/模拟（上游问题）；或 `-cpu` 模型调整
  规避（降低 XNU 对缺失特性的依赖）。


## 9. Bug A 修复 + Bug B 完整侦查（2026-08-31 白天）

### Bug A 已修复 ✅
根因：手写 boot-windows.sh 缺失 fork 标准挂载三要素——`-vga none`、pci-bridge
挂载、`reims-vgpu-gop.rom` 选项 ROM（crates/reims-vgpu-efi 构建的 UEFI GOP 驱动）。
修复后 Windows（TCG 与 WHPX 均验证）串口出现完整引导序列：efi-gop 安装 →
OpenCore EB 日志 → HANDOFF TO XNU。

### Bug B（WHPX + XNU）侦查记录
- 现象：XNU 接管后最早引导阶段死亡，`WHPX: Unexpected VP exit code 4`
  （不可恢复异常）；确定性崩溃签名：页错误 **CR2=0x9e**、CR4=0x20（无 PCIDE）、
  EFER=0xd00（无 NXE）、boot IDT（fffff6af…），两次采样 RIP 仅随 ASLR 变化。
- 帧缓冲取证：pmemsave 提取 8MB 帧缓冲 → 仅 ~1.5% 暗像素（Apple logo 区）、
  零白色文字——XNU 死在打印第一行 verbose 之前（已注入 `-v` boot-args 确认）。
- 已排除/尝试（全部无效）：
  1. 上游 whpx 五补丁之四（xsaves legacy probing 修复、FP 状态 workaround、
     PAT 同步、快速 hypercall）——xsaves 修复使 xsavec 警告消失，崩溃不变；
  2. 强制 CPUID tsc-deadline + arat 位（仿 QEMU 对 X2APIC 的既有先例，
     `whpx_get_supported_cpuid` func 1/6 修复）——警告消失，崩溃签名不变；
  3. `-accel whpx,ssd=off`——无效；
  4. mshv 加速器——`meson: mshv not available on this platform`（QEMU 11 不支持
     此组合），已还原配置。
- 结论：WHPX 下 XNU 极早期（控制台初始化前）确定性页错误于 0x9e；剩余嫌疑
  （MTRR/MSR 处理、EPT 低内存映射、异常投递）需 QEMU whpx 上游工作。证据包
  （寄存器快照、崩溃签名、实验矩阵）已足够提交上游 issue。
- **Windows 通路的可用状态**：设备层全通（NVIDIA 原生 Vulkan + 零拷贝导入 +
  首帧呈现 + GOP 引导 UI），boot 层卡在 Bug B；**WSL/Linux KVM 通路仍是本机
  可用完整通路**。
