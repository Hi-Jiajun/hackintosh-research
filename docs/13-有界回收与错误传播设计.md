# 有界回收与生产错误传播设计（2026-09-08）

> 本文是设计草案，不改变已通过的 v1–v8 契约。实现必须保持 direct Vulkan rail、
> 默认同步模式和现有 capture 不变。

## 1. 问题

当前两个 provider 在“完成观察失败”时的行为不对称，而且缺少显式上界：

- Vulkan：`retire` 把 `PendingExecution` 交给共享 retirement 线程，最多等
  `FENCE_TIMEOUT_NS`（20 秒）；超时后 `ExecutionResources::drop` 将 context
  置为 `poisoned`/`abandoned`，并故意泄漏所有在途 handle 到进程退出。此后
  `ensure_executor_usable` 返回 `provider_unavailable`（`Resource`），没有区分
  “设备丢失”与“放弃预算耗尽”。
- native Metal：completion handler 不回调时，`CompletionRecord` 永远停在
  `Running`；ObjC block 保留 device/queue/pipeline/buffer，Rust 侧没有显式计数
  或上界。deadline 到期只发布 `metal_completion_unknown`，provider 仍可继续接收
  新工作（这是刻意保留的行为，测试
  `deadline_expiry_keeps_the_native_provider_usable` 依赖它）。
- 两者都缺少：可配置的 abandoned 预算、设备丢失快速路径、结构化 health 状态和
  面向生产调用方的“必须重建 provider”错误语义。

## 2. 安全不变量

1. 在活设备上，不得销毁可能仍被 GPU 使用的 Vulkan handle，也不得强制释放
   Metal 的在途 command buffer。
2. 只有 `VK_ERROR_DEVICE_LOST`、`MTLCommandBufferStatus::Error`（或明确的
   device-removal 错误码）才允许进入“资源可销毁/可放弃”路径。
3. 观察超时不是设备丢失；它只能把 submission 移入 abandoned 集合，不能证明
   GPU 已停止。
4. 两个 provider 必须共享同一套 token、终态和 health 语义；错误类别可以不同，
   但 `Retryability` 必须一致。
5. “有界”指 abandoned 集合有显式上界并在耗尽时 fail closed，不指强行回收
   仍可能被 GPU 访问的内存。

## 3. 目标契约

### 3.1 AbandonmentBudget

共享结构（建议放在 `metal-api-core::completion`）：

```text
max_submissions: u64   // 最多允许同时处于 abandoned 状态的 submission 数
max_bytes: u64         // 最多允许 abandoned 的 owned buffer 字节数
record(bytes) -> Admitted | Exhausted
```

- 默认值保持当前行为：Vulkan `max_submissions = 1`（第一次超时即 fail closed），
  native `max_submissions = 8`（handler 仍可能完成，允许有限累积）。
- `max_bytes` 默认与 provider 的 owned buffer 上限一致，避免只按数量计数被大
  buffer 绕过。
- 预算是 provider 级、进程内、单调递增的；不做回收后的“退还”，因为 abandoned
  资源在进程内无法安全释放。

### 3.2 Health

建议在 `metal-api-core::provider` 增加：

```rust
pub enum ProviderHealth {
    Usable,
    /// 设备丢失；新工作必须以 DeviceLost + RetryAfterRecreate 拒绝。
    DeviceLost,
    /// 放弃预算耗尽；新工作必须以 Resource + RetryAfterRecreate 拒绝。
    Exhausted,
}
```

- `Usable`：正常。
- `DeviceLost`：观察到不可恢复的设备错误；Vulkan 可销毁 lost-device 的 handle，
  Metal 可释放 ObjC 引用。
- `Exhausted`：abandoned 预算耗尽；资源仍保留到进程退出，但 provider 不再接收
  新工作。
- 所有 provider 入口（compile/submit/wait/readback/release）在 `health != Usable`
  时返回结构化错误，不允许静默接受新工作。

### 3.3 设备丢失快速路径

- Vulkan `ExecutionResources` 增加 `device_lost: bool`；`PendingExecution::wait`
  返回 `DeviceLost` 时设置该标志，`Drop` 走销毁路径（fence、command pool、
  descriptor pool、pipeline objects、buffers），不再泄漏。
- native `MTLCommandBufferStatus::Error` 需要区分普通命令失败与 device removal；
  后者把 provider 置为 `DeviceLost`，并让 handler 在终态后释放保留对象。
- 两个 provider 的 `wait`/`readback` 必须把 `DeviceLost` 映射为
  `CompletionDisposition::DeviceLost { token: Some(token) }`，对象 API 不得写回。

## 4. 可并行的工作流

| 工作流 | 并行性 | 依赖/冲突 |
|---|---|---|
| 有界放弃 + health + 设备丢失快速路径 | 串行核心 | 修改 `completion.rs`、`provider.rs`、Vulkan `compute_provider.rs`/`lib.rs`、native `native.rs`；定义其他工作流依赖的终态语义 |
| 生产错误传播（对象 API/调用方） | 部分并行 | API 表面可先设计；最终映射依赖 health 枚举 |
| 跨进程 completion 协议 | 串行后继 | 依赖稳定的 token/终态/health |
| completion 驱动的 lease 生命周期 | 串行后继 | 依赖“何时可安全释放资源”的结论 |
| 通用 shader 支持 | 可并行 | 与 completion 路径无代码冲突；可与 v9 语义维度并行 |
| guest memory 生命周期 | 可并行 | 独立模块；alias/映射规则需与 admission 协调 |
| reims 生产接入 | 可并行但受外部阻塞 | 外部仓库；需要 provider 契约稳定 |
| 图形/显示路径 | 可并行 | 大规模独立工作 |
| Windows/RTX 5060 验证 | 完全并行 | 环境依赖，无代码冲突 |
| 上游跟踪（reims PR、metal2vulkan） | 完全并行 | 只读 |

## 5. 实施顺序

1. `AbandonmentBudget` + 纯函数 `drop_policy(submitted, completed, device_lost)`
   及单元测试（不依赖 GPU）。
2. Vulkan：retirement 线程记录 abandoned；预算耗尽 → `Exhausted`；设备丢失 →
   `DeviceLost` + 销毁路径。
3. native：deferred completion 计数；handler 不回调时计入 abandoned；预算耗尽 →
   `Exhausted`；`MTLCommandBufferStatus::Error` 区分 device removal。
4. 对象 API：`DeviceLost`/`Exhausted` 不写回、不重试；`RetryAfterRecreate` 明确
   传给调用方。
5. 验证：现有 151 Rust + 115 Python + v1–v8 五路径全绿；新增预算/health 单元
   测试；Lavapipe 冒烟；macOS 目标 check/clippy。

## 6. 当前不做什么

- 不强行销毁活设备上的在途 handle。
- 不做跨进程 token/lease。
- 不把观察超时等同于设备丢失。
- 不宣称完整 Metal conformance。

## 7. 实施状态（2026-09-08，`8d2a4ca`）

已完成第一步和第二步的大部分：

- `metal-api-core`：新增 `ProviderHealth { Usable, DeviceLost, Exhausted }`、
  `AbandonmentBudget` 和单调 `AbandonmentLedger`；预算语义是“累计达到
  `max_submissions` 或 `max_bytes` 即耗尽”，默认 Vulkan `(1, 64 MiB)`、
  native `(8, 64 MiB)`。
- Vulkan：`VulkanContext` 增加 `health()`、`record_abandonment()`、
  `abandonment_stats()`、`mark_device_lost()`；retirement 线程区分
  `Ok(true)`、超时和非丢失错误，超时按预算决定是否继续；`VK_ERROR_DEVICE_LOST`
  走 `mark_device_lost` + 销毁路径；`ExecutionResources::drop` 的决策抽成纯函数
  `resource_drop_policy(submitted, completed, device_lost)`。
- Vulkan provider：`ensure_context_usable` 把 `DeviceLost` 映射为
  `device_lost` + `RetryAfterRecreate`，把 `Exhausted` 映射为
  `provider_unavailable` + `RetryAfterRecreate`；新增 `health()` 和
  `abandonment_stats()`。
- native：`CompletionSlot` 记录 `owned_bytes`；`fail_deadline` 和
  `release_completion`（仍 running）计入预算；`with_abandonment_budget()`、
  `health()`、`abandonment_stats()` 与 Vulkan 对称。
- native 设备移除：`MTLCommandBufferStatus::Error` 按 `NSError.code` 分类；
  `MTLCommandBufferError::DeviceRemoved`（11）在同步与 completion handler 两条
  路径都设置独立 `device_lost` 标志，`health()` 返回 `DeviceLost`，新工作以
  `metal_device_removed` + `RetryAfterRecreate` 拒绝，且不计入放弃预算；其他
  终态命令错误仍走 `metal_command_failed` + `Exhausted`。
- 对象 API 错误矩阵：submit 期 `DeviceLost`（保留观察 token）与 `Exhausted`
  （`NotSubmitted`）都让 commit 失败、状态为 `Failed`、`wait`/`submission`
  返回同一错误，且不写回任何 host 字节。
- Windows/RTX 5060：`7e67a0e` 的 Windows GNU debug 二进制在 NVIDIA GeForce
  RTX 5060 上跑通 `provider-smoke`（12 项）与 v1–v8 direct/object/async-object
  三条 rail（每 rail 29 cases），v8 raw/wrapped 编码通过；证据在
  `evidence/windows-rtx5060-v8-7e67a0e-2026-09-08/`。文档 `8d2a4ca` 的 CI
  run `34226091972` 四 job 全绿。
- 验证（本地）：100 core + 9 native + 36 Vulkan + 14 capture Rust 测试通过，
  115 Python 通过；fmt/clippy/rustdoc、macOS ARM64 check/clippy、Lavapipe
  standalone/provider-smoke/v8 direct/async 通过。云端 CI run `34225380992`
  四 job 全绿（standalone 159 Rust + 115 Python；macOS runner 上 native 为 10，
  含 macOS-only 分类常量测试；五路 v1–v8 一致）。证据在
