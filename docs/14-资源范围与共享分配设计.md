# 资源范围 hazard 与共享 per-allocation GPU buffer 设计（2026-09-11）

> 本文是设计草案，不改变已通过的 v1–v9 契约。实现必须保持 direct Vulkan rail、
> 默认同步模式、对象 API 现有语义和现有 capture 不变；每一步都要能单独跑 CI 与
> 真机验证。相关文档：`docs/11-Metal-provider-contract-v0.md` §4/§11（alias 与
> open decisions）、`docs/13-有界回收与错误传播设计.md`（回收/丢失语义）、
> `HANDOFF-2026-09-09-QUEUE-SCHEDULING.md` §3/§4/§6。

## 1. 问题

当前的对象 API 用**整 allocation 独占**表示“命令在途”：

- `crates/metal-api-core/src/provider_api.rs` 的 `BufferReservation`（317 行）是
  一个 allocation 级的独占锁：`Buffer::reserve`（298 行）在计数非零时等待，
  `reserve_buffers`（353 行）按 identity 顺序保留**每个 pass 用到的全部
  allocation**，直到 command buffer 完成才释放；
- 结果是两个 command buffer 即使只写同一个 buffer 的不同区间（disjoint
  ranges）也会串行——队列调度（`2fda388`/4181b08` 的每 queue host lock、
  专用 compute family、最少在途选择）在真实负载下被这一层独占抹平；
- 同一 backing 的多 view alias 至今被拒绝：contract v0（`docs/11` §4）明确
  “为了 MVP 拒绝同一 backing 的多 binding alias，这项 refusal 仍然有效，直到
  alias contract 和 parity case 完成”，而 §11 把“overlapping writable alias 的
  deterministic merge/writeback 规则”列为 open decision。**本文就是这份 alias
  contract 的第一版**；
- 这一层同时是 guest memory 的前置：guest allocation 会有多个 view（驱动按
  wire 命令给不同 offset），只有 range 级 hazard 成立后，guest page 的宿主映射、
  脏页写回、部分失效才有可以挂靠的语义。

目标：

1. 同一 allocation 的多个 disjoint view 可以在同一 trace、多个在途提交中共存；
2. 用 **range 级 hazard** 取代 allocation 级独占，同时保持提交与写回的字节级
   确定性；
3. 第一版不引入 GPU 统一别名（共享 device buffer 的完整形态），把风险留给
   独立增量；
4. 为 guest memory 生命周期准备 owner 侧的语义（哪些 range 在途、由谁写回）。

## 2. 安全不变量

1. **重叠写必须被拒绝或串行化**，不能依赖“最后写赢”这种未证明的时序。无法
   证明 disjoint 时 typed-refuse。
2. **读必须看到确定版本**：range 级 hazard 必须同时覆盖 read↔write，而不是只
   比较写集合。
3. **写回规则唯一且顺序稳定**：同一 allocation 的最终字节必须由一条确定的
   merge 规则给出（见 §3.4），不能依赖提交完成顺序的偶然性。
4. **能力门控**：新语义挂在 `ProviderCapabilities` 上，未声明的 provider 行为
   与输出不变；旧 suite（v1–v9）与 direct rail 不变。
5. **回收语义沿用 docs/13**：range 集合是“在途资源”的一部分，设备丢失/放弃
   路径必须能把它一并退休；超时不是设备丢失。
6. **不新增 GPU 可见性假设**：第一版仍是 host-visible 写回落地，不承诺 GPU 侧
   直接互见（那是共享 device buffer 增量的事）。

## 3. 目标契约

### 3.1 Alias 模式与能力位

`AliasMode`（`crates/metal-api-core/src/provider.rs` 2599 行）现有三个取值：
`Refused | DistinctViews | ExplicitPolicy`。本设计把 `DistinctViews` 的语义钉死：

- **同一 allocation 的多个 view**：两两 range 不重叠 ⇒ 允许；任何重叠（含
  读读；读读是否放行见 §8 开放问题）⇒ 第一版仍拒绝 `buffer_alias_unsupported`；
- **同一 view 的跨 pass 复用**：维持现状（已允许）；
- **声明方式（2026-09-11 实现决定）**：不新增 capability 字段——`AliasMode::
  DistinctViews` 本身就是声明，admission 在该模式下按 range 放行 disjoint
  多 view，重叠仍拒绝。理由：避免改动 `MCC1` 能力帧的线格式；未声明
  （`Refused`/`ExplicitPolicy`）的 provider 行为不变，生产 provider 在 Step 4
  之前继续使用 `Refused`。

### 3.2 Range 级 hazard

定义（建议放 `metal-api-core::provider`，与 alias admission 同文件）：

```rust
/// 提交时解析出的访问集合，单位是 view range。
pub struct RangeSet {
    pub writes: Vec<BufferRange>,   // (allocation_id, offset, length)
    pub reads: Vec<BufferRange>,
}
```

规则：

- 冲突定义：`new.writes ∩ (inflight.writes ∪ inflight.reads)` 或
  `new.reads ∩ inflight.writes` 非空 ⇒ 冲突；
- 冲突时沿用现有“按 identity 顺序等待”的串行化路径（保持确定性），不引入
  重试/优先级；
- 无冲突 ⇒ 允许并发在途（host enqueue 已支持，probe 可断言）；
- 读取集合只用于 hazard，不产生写回。

### 3.3 共享 per-allocation GPU buffer：两条实现路线

**路线 B（建议第一版）**：保留“每 view 一个 device buffer”的现状
（`metal-api-vulkan/src/lib.rs` 1579 行的 `GpuBuffer`、每次提交的
copy-in/copy-out），只把 **reservation 换成 range 集** 并在提交边界做
**部分写回合并**。改动局部、CI/Lavapipe 可验证、真机可复现。

**路线 A（guest memory 阶段的入口）**：device buffer 覆盖整个 allocation（或
覆盖并集的共享 buffer），view 是窗口。它更接近 guest 映射（一次 import、
copy 一次），但引入 GPU 侧同步/可见性与 Windows/WHPX 上的映射复杂度，作为
独立增量另行设计。

### 3.4 写回合并规则

- 一次提交内：同一 allocation 的多个写 range 若重叠 ⇒ admission 拒绝；不重叠 ⇒
  各自报告；
- 跨提交：若两个 in-flight 提交的写 range 重叠且被允许（未来策略）⇒ 按
  **提交顺序**后者胜出；第一版通过 hazard 直接禁止并发，不存在该情况；
- canonical order：`allocation_id` 升序 → `range.offset` 升序 →
  `range.length` 升序；报告顺序稳定；
- 现有 `BufferWriteback { view_id, allocation_id, offset, bytes }` 已携带 range，
  **报告格式不变**；变的是 reservation 与 merge 的粒度。

### 3.5 对象 API（provider_api.rs）

- `BufferReservation` 扩展为 range 集：`reserve(&[(AllocationId, Range)])`。
  实现建议：每 allocation 一个 `RangeBoard`（`BTreeMap<(start,end)>` + 在途
  owner 计数），等待条件从“计数为 0”改为“与在途集合无冲突”；释放时按
  range 摘除并唤醒等待者；
- `Buffer::read`/`write`（CPU 访问）与在途 range 的互斥：写范围冲突时等待，
  读范围与写范围冲突时等待（保守；读读放行）；
- admission 放宽（§3.1）后，对象 API 的 pass 记录允许多 view per allocation；
  其余校验不变；
- 异步/取消路径（`cancel`）必须把 range 集随 submission 一并退休，避免泄漏。

### 3.6 跨进程 / lease / IPC 影响

- staged lease 与 borrowed no-copy 的“映射必须覆盖 reservation”校验：措辞更新为
  “覆盖本次提交的全部 range”；descriptor 传递与 `MCC1` 帧不变；
- 设备丢失/放弃：range 集进入 docs/13 的 abandoned 集合，进程退出前不强行回收；
- dma-buf 不是 Windows 目标，保底仍是 host-pointer/no-copy。

## 4. 替代方案与取舍

| 方案 | 取舍 |
|---|---|
| 维持整 allocation 独占 | 队列调度收益被抹平，guest memory 无挂靠点；不选 |
| 直接做共享 device buffer（路线 A） | 一次 import 的收益吸引人，但同步/可见性/Windows 映射复杂；推迟 |
| 更细粒度（view 内 sub-range） | 第一版不拆 view 内部；驱动实际会用多 view 表达不同区间 |
| 全局串行 | 简单但抹平并发；不选 |
| 重叠写“最后写赢” | 未证明的时序语义；第一版拒绝 |

## 5. 实施顺序（每步独立可验证）

1. **core 类型与纯逻辑**：`RangeSet`、冲突判定、merge/canonical order 纯函数 +
   穷尽单测；不接线，无行为变化。CI：cargo test/clippy。
2. **admission 放宽**：`alias_distinct_ranges` 能力位 + `DistinctViews` 语义；
   trace 级 disjoint 多 view 放行、重叠仍拒绝；core 与对象 API 单测。
3. **range reservation（provider_api）**：`BufferReservation` → range 集；
   `reserve_buffers` 改为按 range 登记；新增两个 command buffer disjoint range
   并发用例（probe-backed，断言同时持有）；CI + RTX 5060 真机。
4. **provider 落地**：Vulkan（路线 B：每 view buffer + 部分写回合并）与 native
   （同一 MTLBuffer 多 view）实现；断连/丢失回收路径更新。
5. **conformance v10 维度**：`suite-v10` = “同一 allocation 的 disjoint 多 view”
   fixtures（在 v7 subset_chain 池上新增一个共享 allocation 的读写 view 组合），
   五路径 compare + RTX 5060 真机 + evidence 归档。**这是把本设计变成外部可
   验证事实的一步**（此前 v10 候选“更复杂 buffer 布局”正被本设计解锁）。
6. **（可选）共享 per-allocation device buffer（路线 A）**：guest memory 的
   入口设计，另文。

## 6. 验收标准

- 同一 allocation 两个 disjoint 写 range 的两个 command buffer：host enqueue
  并发（probe 证明同时持有）、写回字节精确、五路径（native/vulkan/objects×2）
  一致；
- 重叠（读-写、写-写）仍 typed-refuse，slug 稳定（`buffer_alias_unsupported`
  或其细分变体，旧 slug 语义兼容）；
- v1–v9 全部不变；direct rail 与默认同步模式不变；Windows RTX 5060 与 Lavapipe
  均通过；CI 五 job 绿；
- 设备丢失注入回归中 range 集随 submission 退休，无泄漏。

## 7. 边界（本设计不做）

- 不做 view 内 sub-range 拆分；
- 第一版不做重叠写的合并/顺序语义（拒绝）；
- 不做共享 device buffer（路线 A）的完整实现；
- 不涉及 guest memory 生命周期本身（导入、脏页、失效、迁移）；
- 不做跨 device/跨 provider 别名。

## 8. 开放问题

- 只读重叠是否放行（收益是共享读的并行度，代价是 read↔read 也要进 hazard 图）；
- `DistinctViews` 下 writeback 报告粒度：逐 view 还是按 allocation 合并
  （影响 compare 的 v10 规则）；
- 与 `VK_EXT_external_memory_host`/共享 section 的交互：路线 A 落地时 range 是否
  需要按页对齐；
- 与 queue priority/公平性的交互：range hazard 是否作为调度的第二维度。
