# 共享 per-allocation device buffer 与宿主字节互斥设计（2026-09-13）

> 本文推进 `research/docs/14` 的 Step 6，并收口 Step 3 留下的边界。步骤 1（宿主字节
> 互斥）已可直接实现；步骤 2 起（路线 A 共享 device buffer）是 guest memory 的入口，需要
> 本文的判据。相关：`docs/13`（回收/丢失）、`docs/14` §3.2/§3.4/§8。

## 1. 起点：Step 3 留下的边界

Step 3（`fb5f8fd`）把 `BufferReservation` 改成 range 集，所以两个命令可以同时持有同一
allocation 上不相交的 range。但对象 API 的 `execute` 仍然：

1. 为每个 reservation 取一个 **整 allocation** 的 `Mutex<Vec<u8>>` guard；
2. 在 guard 之下把每个 view 的字节**拷贝进 trace**（`BufferSource::OwnedBytes`）；
3. **持有这些 guard 跨越 `provider.submit`**，直到 `CompletedVisible`（原地落地）或
   `Submitted`（交给 pending）才 `drop`。

第 3 步是残留串行的来源：异步模式下 guard 在 submit 返回时释放（所以
`disjoint_ranges_of_one_allocation_stay_in_flight_together` 通过），但**同步模式下 guard
覆盖整个 GPU 执行期**，于是同一 allocation 上不相交的兄弟命令仍会在 `lock_bytes` 上排队。

## 2. 关键结论：不需要 chunk 锁，只需要提前释放 guard

原本设想的方案是把 `Mutex<Vec<u8>>` 换成按 chunk 的锁表。重新审视后这**不必要**，因为
CPU 访问与命令之间的互斥**已经由 reservation 承担**：

- `Buffer::read`/`write` 走 `lock_unreserved(start, end, write)`：先在 reservation 板上
  按 range 等待，**拿到字节 guard 之后再复查一次 reservation** 才返回。所以
  "CPU 访问相对 commit 快照的线性化点"是**字节 guard**，而"命令在途期间禁止冲突 CPU 访问"
  是**reservation**。
- `execute` 需要的只是"快照期间字节稳定"。快照一旦拷进 trace，provider 全程不再触碰宿主
  字节（`BufferSource::OwnedBytes` 是拷贝），因此 guard 在 submit 之前就可以释放。

于是：

- 命令 A（写 [0,4)）在 submit 中停留时，命令 B（写 [4,8)）可以拿字节 guard 做自己的快照，
  因为 A 已经释放；B 的 reservation 与 A 不相交，所以 `reserve_ranges` 也放行。
- 若 B 的范围与 A 相交，B 在 `reserve_ranges` 就等待 → 行为不变。
- CPU 写 [0,4) 在 A 在途时仍会等待：它复查时看到 A 的写 range。
- 落地阶段 `apply_writebacks` 自己重新取 guard，与快照的线性化无关。

**这不改变任何可观察的字节结果**，只把"整 allocation 在同步提交期间被独占"这一条去掉。
chunk 锁只在"希望两个不相交命令的快照/落地阶段也互不阻塞"时才有额外收益，那是纯粹的
互斥量竞争优化，不是正确性需求，本文不做。

## 3. 路线 A：共享 per-allocation device buffer

### 3.1 它是什么

现状（路线 B）：pool 里每个 view 一个 device buffer，每个 buffer 覆盖该 view 的字节。改为：
**每个 allocation 一个 device buffer**（大小 = allocation size），view 是它上面的
`(offset, length)` 窗口，绑定用 `DescriptorBufferInfo { offset, length }`。

### 3.2 它买什么、不买什么（必须说清楚）

**买到的**：
- 每提交每 allocation **一次** copy-in 与一次 copy-out，而不是每 view 一次；
- guest memory 的入口：一个 allocation 一次 import / 一次映射 / 一份脏页记账，这正是
  `docs/14` 说它是"guest memory 前置"的含义；
- 未来表达**重叠** view（同一 backing 的 alias 合并/写回规则）时唯一的可实现基础。

**买不到的（重要）**：它**不改变 disjoint view 的正确性判据**。两个不相交 range 无论共享
还是分开 device buffer，都不可能交换数据——每个 view 的 footprint proof 把自己的访问限制在
半开区间内。所以路线 A 是**效率与集成**的改动，不是正确性修正；不要为它编造一个
"跨 view 数据流"的 conformance 判据。

### 3.3 可验证判据

- **上传/回读计数**：`provider-capture` 与 `provider-smoke` 报告每提交的 copy-in / copy-out
  次数；同一 allocation 的 N 个 view 在同一提交内必须报 N→1。这是可观察、可归档的判据。
- **字节精确性回归**：v1–v10 五路径必须完全不变（共享 buffer 下写回仍是每 view 切片，
  `BufferWriteback { allocation_id, offset, bytes }` 格式不变）。
- **能力门控**：新语义挂在 `ProviderCapabilities` 上；未声明的 provider 行为与输出不变。

### 3.4 与写回合并的关系

`docs/14` §3.4 的"部分写回合并"在路线 A 下变得自然：一次 copy-out 拿到整块 allocation 的
落地字节，再按 view 的 `(offset, length)` 切片成多条 `BufferWriteback`。canonical order
仍是 allocation → offset → length。**报告格式与顺序不变**，所以 v1–v10 的 compare 规则不需要
改。

## 4. 替代方案与取舍

| 方案 | 取舍 |
|---|---|
| chunk 锁表 | 只有互斥量竞争收益，无正确性收益；不选（§2） |
| 提前释放 guard（本文步骤 1） | 最小、可证伪、直接去掉同步提交的整 allocation 独占；选 |
| 每 allocation 一个 device buffer（路线 A） | 一次上传/回读 + guest memory 入口；选为步骤 2 |
| 分块 device buffer（与 guest 页对齐） | 与页面粒度天然匹配，但 view 跨块时绑定需要多段；推迟 |
| 保持每 view 一个 buffer | 无法一次导入，guest memory 无挂靠点；不选 |

## 5. 实施顺序（每步独立可验证）

1. **提前释放宿主字节 guard**（本文 §2）：`execute` 在 trace 快照完成后、`provider.submit`
   之前 `drop(guards)`；新增 gate-backed probe：命令 A 停在 submit 内时，命令 B（不相交 range）
   必须能完成 commit。探针需**证伪**（把 guard 放回 submit 之后即失败）。
2. **Vulkan 共享 device buffer**：pool 改为每 allocation 一个 `GpuBuffer`；
   `create_buffers` 按 allocation 去重；绑定用 view 偏移；copy-out 按 view 切片。
   `provider-smoke` 增加同一 allocation 多 view 的执行用例并报告 copy 计数。
3. **native 对称实现**：一条 `MTLBuffer` 多 view（`newBufferWithBytes` 一次，
   绑定时用 `offset:`）。
4. **部分上传/回读**：只搬运本提交触及的 range（用 access + footprint 推断），
   其余保持。纯性能步。
5. **conformance v11**：把"每 allocation 一次上传/回读"变成外部可验证事实——
   capture 报告新增分配级 copy 计数，五路径 compare 校验计数而非新增语义。
   **注意**：v11 校验的是计数契约，不是新的字节语义；不要把它写成"跨 view 数据流"。
6. **guest memory 接口**：另文。

## 6. 验收标准

- 步骤 1：gate-backed probe 通过且可证伪；v1–v10 五路径不变；CI 五 job 绿；RTX 5060 通过。
- 步骤 2/3：同一 allocation 的 N 个 view 在同一提交内只报一次 copy-in / 一次 copy-out；
  写回字节与 v1–v10 完全一致；Lavapipe 与 RTX 5060 双跑。
- 步骤 5：五路径 capture 的分配级计数一致。

## 7. 边界（本文不做）

- 不做重叠 view 的合并/写回顺序语义（仍拒绝）；
- 不做 view 内 sub-range 拆分；
- 不做 chunk 级宿主字节锁（§2 已论证无正确性收益）；
- 不做 guest memory 生命周期本身（导入、脏页、失效、迁移）；
- 不做跨 device / 跨 provider 别名。

## 8. 开放问题（承接 `docs/14` §8）

- 只读重叠是否放行；
- 路线 A 下 range 是否需要对页对齐（与 `VK_EXT_external_memory_host` / 共享 section 的交互）；
- 分配级 copy 计数是否需要成为 `ProviderCapabilities` 的一部分（用于 compare 门控）；
- range hazard 是否作为队列调度的第二维度。

## 9. 实施状态

  `drop(guards)`；残留的串行来源（同步提交期间整 allocation 被字节 guard 独占）消失。
  探针 `a_parked_submit_does_not_hold_host_bytes_for_a_disjoint_range` 用 gate 把一条命令停在
  `submit` 内，要求同一 allocation 上不相交 range 的 CPU 写必须在 10 秒内完成、重叠 range 的
  CPU 写必须继续等待；**已证伪**——把 guard 重新持有跨 submit 即以上述预期信息失败。
  验证：CI run `34739393800` 五个 job 全绿（五路径 v1–v10 parity 不变）；Lavapipe

  注意：RTX 5060 那次运行**不能**区分 guard 是否被提前释放（既有并发用例走异步路径，
