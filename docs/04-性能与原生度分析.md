# 性能与原生度分析：虚拟 Apple GPU 路线 vs 裸金属黑苹果

> 数据来源：repos/fork-reims-vgpu/AGENTS.md、crates/reims-vgpu/src/env.rs 的内嵌测量、
> repos/27on86/docs/experiments/。所有数字都是 macos-13 rail 上驱动型 boot 的一手测量；
> 注意 AGENTS.md 的纪律：快/慢 boot 是两个群体，读数必须注明来自哪个群体。

## 1. 结论先行

不存在单一百分比。按组件拆分：

| 组件 | 硬件加速路径（KVM/HVF/WHPX） | TCG 软件翻译路径 |
|---|---|---|
| CPU | **≈95%+ 原生**（典型虚拟化开销 1-5%） | **数量级差距**（10x+），不可日用 |
| GPU 着色器执行 | **≈原生**（宿主 GPU 跑翻译后的 SPIR-V，ISA 翻译不影响执行速度） | 同左，但喂不饱 |
| 每 draw 的宿主侧税 | 好宿主 ~13 µs CPU/draw（合成器负载） | 叠加在慢 CPU 上，雪上加霜 |
| 桌面合成帧率 | **95-117 Hz**（fast 群体，present 零丢帧） | 极慢 |
| 内存 rails | 零拷贝导入 ≈ 2x 拷贝路径帧率 | 同左 |

**定性结论**：在 KVM/HVF 这类硬件加速宿主上，**CPU 侧和着色器执行侧都已经接近原生**；
剩余差距集中在"每 draw 的宿主侧税"（解码+提交+内存搬运）。对桌面合成这种负载，
现有数据支持"体感接近原生"；对游戏/3D 重负载，**没有基准数据，不能下结论**（且 alpha
阶段的正确性缺口比性能缺口更先咬人）。

## 2. CPU 侧

- KVM（Linux）/ HVF（macOS）/ WHPX（Windows）都是硬件虚拟化，客户机指令在物理核上
  直接执行，开销主要来自 vmexit 频率——CPU 密集负载典型损失 1-5%。
- 旧裸金属黑苹果 CPU 是 100% 原生；硬件虚拟化路径追平到 95%+ 是行业共识量级
  （Apple VZ 的 Geekbench 实测也是这个范围）。
- TCG（x86 宿主跑 arm64 macOS 的唯一选项）是软件翻译：27on86 实验记录显示引导要
  数分钟、客户机时间需要特殊伸缩策略（E0005：串行 CPU 启动阶段先快后慢的时间换算），
  属于研究/开发环境，与"原生"差一个数量级以上。

## 3. GPU 侧的解剖：开销在哪里

```text
客户机 Metal 命令流
   │ ① 解码（宿主 CPU，每 draw 一次）
   ▼
设备模型 / 调度（宿主 CPU）
   │ ② 着色器翻译 AIR→SPIR-V（每 pipeline 一次，按内容缓存）
   ▼
宿主 Vulkan/Metal 执行（宿主 GPU，原生速度）
   │ ③ 内存 rails（每帧多次）
   │    零拷贝 host-pointer 导入：~0 税
   │    拷贝 rails：writeback 拷贝是大头
   ▼
呈现（present/offered 已做到 1.000 零丢帧）
```

**①和③是仅有的新增税，②是一次性成本。像素/着色器执行本身（GPU 时间）没有翻译税。**

## 4. 一手测量

### 4.1 合成器负载（macos-13，驱动型 boot，x86 客户机 + Linux KVM + Vulkan）

fast boot 群体，shipping 构建（AGENTS.md，离散 NVIDIA 宿主，51% GPU 占用）：

| 指标 | 数值 |
|---|---|
| present_hz（= offered_hz） | **113.2**（109.8-116.3，n=5） |
| CPU us/draw | **13.21**（12.66-14.02） |
| 每 draw GPU 时间 +20.6% 的对照臂 | present_hz 105.5，us/draw 15.07（两臂不相交） |

- slow boot 群体恰好 60 Hz（客户机合成器按合成的 1/60 秒节拍走，与设备无关）；
- iGPU 宿主上 CPU 9 µs + GPU 10-12 µs / draw，二者之和 × draws/s ≈ 每个忙碌秒的
  95-100%——**该通路当前被 per-draw 成本饱和**。

### 4.2 内存 rails 对照（env.rs 内嵌测量，较旧构建）

| | import on | import off（纯拷贝） |
|---|---|---|
| present_hz | 14.80 | 6.80 / 6.85 |
| draw_us/draw | 41.4 µs | 126.3 / 127.8 µs |
| ExecPhase::Finish | 639.6 ms/s | 810.9 / 821.1 ms/s |

**零拷贝 vs 拷贝 ≈ 2x 帧率、1/3 每 draw 成本**——这是结构性的最大单项差距。
（该表的绝对值低于 4.1，因为测量早于 presenter 修复；比值仍然有效。）

### 4.3 离散 GPU 的补集观察（env.rs 更新的 regime-matched 测量）

import on/off 在离散宿主上**帧数相同**：差别只是"拷贝由谁做"——import on 时 GPU
gather 走 PCIe（4.46 GB/s @ ~18 GB/s 有效，占 GPU 时间 ~55%），import off 时 CPU
drain worker 打包。宿主不同，瓶颈搬家。

## 5. 对比旧裸金属方案

| 维度 | 裸金属黑苹果（Intel + AMD GPU） | 新方案（虚拟 Apple GPU） |
|---|---|---|
| CPU | 100% 原生 | 95%+（硬件虚拟化） |
| GPU 驱动 | Apple 官方 Metal 驱动跑真硬件 | 客户机用 Apple 官方 paravirt 驱动，宿主端第三方实现 |
| 着色器 | Apple 编译产物直跑 | 翻译后跑宿主 Vulkan/Metal，执行速度原生 |
| 瓶颈形状 | 驱动兼容性、单线程 CPU | 每 draw 宿主税、翻译覆盖度 |
| 兼容风险 | 硬件/系统版本锁死（路线已死） | alpha 语义缺口（会拒绝/回退，见 fail log） |

旧方案的"100%"是它的天花板也是它的终点；新方案的可移植性换来的是 13 µs/draw 量级的
税和未完成的翻译覆盖率。**对日常桌面负载，现有数据（100+ Hz、零丢帧）说明这税已经
小到体感可忽略；对重 GPU 负载没有数据。**

## 6. "近乎原生日用"的判定

| 场景 | 判定 |
|---|---|
| 桌面/浏览器/终端/Xcode/办公 | KVM/HVF 路径：**数据支持接近原生体感**；Windows 路径未验证 |
| GPU 计算（如 llama.cpp/Metal 推理） | 结构上可行（外部参考：VZ 客户机开 Metal 后推理加速 11-16x），reims 无基准 |
| 游戏/实时 3D | 无数据；翻译覆盖缺口会以 FALLBACK/decline 形式显现 |
| Windows x86 宿主跑 arm64 macOS（TCG） | 不可能近乎原生；开发环境定位 |

## 7. 差距还能收窄多少

1. presenter 曾把帧率钳在 ~41 Hz，已修复（present/offered = 1.000）；
2. 零拷贝导入是 2x 级别的杠杆——Windows ICD 的 VK_EXT_external_memory_host 实测是
   移植阶段的关键检查项；
3. 13 µs/draw 的解码+提交路径仍在被上游持续优化（每个改动都有 n≥3 对照 boot）；
4. Apple Silicon 宿主上的 Metal-direct 后端与 Apple 自家 VZ 同构，上限就是 VZ 的水平；
5. 慢 boot 群体（恰好 60 Hz）根因已定位为客户机合成器节拍，不是设备缺陷。

**一句话**：硬件虚拟化宿主上，CPU 已经原生级；GPU 的着色器执行是原生速度，税在每 draw
的宿主侧处理上，目前小到合成器能跑 100+ Hz——但"跑得和裸金属一样快"只对桌面类负载有
数据支撑，游戏与 3D 要等翻译覆盖率和基准。
