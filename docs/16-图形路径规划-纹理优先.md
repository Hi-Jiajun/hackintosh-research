# 图形路径规划：从纹理开始（2026-09-13）

> 本文是图形/显示路径的启动规划。当前的 provider 契约、conformance 矩阵与比较器都建立在
> buffer compute 子集上（v1–v10），本文只定义**第一步**与依赖顺序，不改动已通过的契约。
> 相关：`docs/09`（总目标与三道门）、`docs/14`/`docs/15`（range hazard 与共享分配，纹理
> 的 backing 会复用这套语义）、`docs/13`（回收与设备丢失）。

## 1. 为什么要先做纹理

`docs/09` §13.3 把图形路径列为未实现：纹理、render pass、sampler、render pipeline、
presentation、swapchain、heaps、ICB。它们不是并列关系，有依赖序：

```text
纹理资源（创建/写/读/格式） → sampler → 纹理读取的 compute 用例
   → render pipeline（顶点/片元） → render pass 与附件
   → presentation / swapchain → heaps / ICB
```

纹理同时是**唯一一个可以继续用现有 compute 轨道验证**的图形特性：一个 compute kernel
读取 2D 纹理、写入 buffer（或反向），五路径比较器只需在 buffer 之外增加"纹理采样结果"
这一观测面。因此第一步选纹理，而不是 render pass。

## 2. 已经具备的条件（无需重新发明）

pinned 的 metal2vulkan（`43c46ac`）已经为纹理准备好了接口，provider 只需要接上：

- `reflect::ResourceAccess` 已有 `Sampled`（`OpTypeImage Sampled=1`）与 `Storage`
  （`Sampled=2`）两个取值，buffer 访问分类（`Unused/ReadOnly/WriteOnly/ReadWrite`）保持不变；
- `ResourceBinding::texture_shape` 与 `DescriptorLocation`（set/binding/count）描述了纹理的
  descriptor 位置与形状要求；validation 侧的 executor contract 已覆盖
  `texture2d_ms`、`texture_buffer`、`texture2d<uint, write>` 等边界，以及
  `air.sample_texture_*`、`air.gather_texture_2d` 这些 intrinsic 的合法性检查；
- `SynthesizedNullTexture` / `SynthesizedReadSampler` 说明 translator 会在 `air.get_null_texture_2d()`
  与 `air.get_read_sampler()` 处要求 consumer 提供真实 image/sampler——这正是 provider 的
  admission 需要显式支持或拒绝的两类占位资源。

当前阻塞点在 core：`BufferAccess` 只有 buffer 四态，`ValidatedComputeTrace` 的资源池只有
`BufferView`。`Sampled`/`Storage` 目前会被保守地当成可写 buffer 处理（见
`docs/09` 流水线与 `crates/metal-api-vulkan/src/lib.rs` 的访问分类），这在新契约落地前是
**安全但不可用**的。

## 3. 第一步的增量定义（建议）

**目标**：同一个 compute kernel 在五条路径上对同一张 2D 纹理采样，并把结果写入 buffer；
byte 级 parity 由现有比较器扩展到"纹理观测"。

1. **core 契约**（`metal-api-core/src/provider.rs`）
   - 新增 `TextureId`/`TextureView`（type、format、size、mip/array 维度、usage）与
     `TextureResource`（source：owned bytes / staged / borrowed）；
   - `ResourceAccess` 增补 `Sampled`/`Storage` 的稳定映射（不改变 buffer 四态语义）；
   - `ComputeTrace` 的资源池扩展为 buffer + texture，`MAX_SERIAL_RESOURCES` 复用；
   - 与 range hazard 的关系：纹理按"整资源在途"预约起步，subresource 并发留到后续文档。
2. **Vulkan provider**：`Sampled` → `vk::Image`（`VK_IMAGE_TYPE_2D`、线性 tiling、host-visible
   上传一次）；`Storage` → storage image；descriptor 按反射的 set/binding 绑定；采样器用
   pinned translator 的 sampler 描述（nearest/linear + clamp 起步）。
3. **native provider**：`MTLTexture`（`StorageModeShared`，`replaceRegion` 上传，
   `getBytes` 回读）；sampler 状态与 Vulkan 对齐。
4. **conformance v11**：一个新 fixture `sample_texture_2d`（4x4 RGBA8 输入纹理 + 4 字节输出
   buffer），Swift oracle 用 `MTLTexture` + 同样的 MSL 采样；比较器增加纹理观测字段
   （采样结果已经在 buffer 里，所以第一版可以完全复用现有 buffer 比较器——这是选纹理的
   另一个理由）。
5. **验收**：五路径 parity（v1–v10 不变 + v11 通过）；Lavapipe 与 RTX 5060 真机；
   CI 五 job 绿；证据归档。纹理读取的操作计数沿用 `copy_in/copy_out` 的组织方式，
   但需要先定义"纹理的 copy 单位"（建议按 texture resource，不按字节）。

## 4. 开放问题（实现前需要先定）

- `Sampled`/`Storage` 是否进入 `ProviderCapabilities`，还是按现有 `AliasMode` 的方式由
  provider 声明支持面？
- 纹理的"在途"语义：整纹理独占 vs subresource range（与 `docs/14` 的 range hazard 对齐）。
- 格式矩阵：第一版只支持 `RGBA8Unorm`、`R32Uint`、`R32Float` 中哪一个（取决于 `copy_word`
  类 fixture 的最小可行集）。
- `SynthesizedNullTexture`/`SynthesizedReadSampler`：第一版是显式 typed-refuse（推荐），
  还是必须支持（否则某些真实 shader 无法进入）？
- 纹理的 writeback 语义：`Storage` 纹理是否需要与 buffer 相同的字节精确回读。

### 4.1 建议决策（2026-09-13，待实现验证）

下表给出每一问的**建议答案**与理由，实现时按此推进；任何一条被实测推翻都要回写本节。

| 问题 | 建议决策 | 理由 |
|---|---|---|
| 能力声明 | 新增 `TextureSupport` 能力位（`Sampled`/`Storage` 分开），默认关闭 | 与 `AliasMode` 的显式声明风格一致；旧 provider 行为不变，比较器按能力门控 |
| 在途语义 | 第一版：整纹理在途；subresource range 留给后续文档 | `docs/14` 的 range hazard 是为 buffer 半开区间设计的；纹理 subresource 的跨界语义（mip/array slice）需要单独设计，先不混入 |
| 第一版格式 | `R32Uint`（先）→ `RGBA8Unorm`（随后） | `R32Uint` 的字节序与 `copy_word` 类 fixture 完全同构，比较器不需要新观测面；`RGBA8Unorm` 涉及采样滤波，放在 sampler 决策之后 |
| 占位资源 | 第一版 typed-refuse（`slug = synthesized_texture_unsupported`） | `air.get_null_texture_2d()` 的 null 语义（读为 0）可以先拒绝；等真实 shader 需要时再实现，避免把未验证的语义写进契约 |
| Storage 写回 | 第一版不做 `Storage` 的字节回读，只做 `Sampled` 读路径 | 写回语义要与 `docs/14` 的写回合并规则对齐；先把只读采样打通，避免同时引入两个未验证面 |
| 比较器观测 | 采样结果写入 buffer，比较器零改动 | 这是选纹理作第一步的核心理由；纹理本身不进 capture 报告，copies 计数也暂不扩展 |

配套的落地顺序（每步独立可验证）：

1. `metal-api-core`：`TextureId`/`TextureView`/`TextureFormat`/`TextureType`/`TextureSource` 纯类型 +
   校验单测（零行为变化，照 `docs/14` Step 1 的先例）；
2. `ComputeTrace` 资源池扩展：pass 增加纹理绑定槽，`serial_resources` 归一化；
3. Vulkan provider：`Sampled` → `VkImage` + 采样器（nearest/clamp）；
4. native provider：`MTLTexture` 对称实现；
5. conformance v11 fixture + CI 五路径；证据归档。

### 4.5 多线程纹理读取的实测缺陷（2026-09-13 晚，待修）

把 fixture 的 1x1 dispatch 换成 NxN 后**只有前两个线程的写回被观测到**：

- 输出 buffer 加大到 64 字节（fixture 的 `air.buffer_size` 已更正为 64，`afaf893`），
  1x1 情况仍正确（首个 texel = 0）；
- 2x2 网格（4 线程）实测 `[0,1,0,0,0,...]`——线程 0/1 写入值为 0/1 的 texel，线程 2/3
  没有落地；
- 这不是测试对线程顺序的假设问题（前两线程的取值本身就依赖 y=0 行），而是**多 invocation
  下读或写回路径的真实缺陷**。首要嫌疑：`air.read_texture_2d` 的坐标向量构造
  （`and`/`lshr` + `insertelement`）在非零 invocation 上未被 translator 正确降级，
  或写回路径按 invocation 去重/截断。
- 排查入口：对该 fixture 做 2x2 dispatch，检查 translator 的 SPIR-V（`OpReadClockKHR`
  无关；看 image 读的坐标来源与 storage buffer 的写地址），以及 `read_updates` 对多
  invocation 写回的切片逻辑。修好之前，v11 conformance 的纹理用例应先保持单线程，
  或在需要并行时先补线程组内存/barrier 的显式用例。

**进一步诊断（同日，三个探针，全部已清理）**：

1. 2x2 dispatch、local [2,2,1] 与 local [1,1,1]（4 个 group）**都**只落地 0/1 两个值；
   读回长度 64 正常，所以不是回读截断。
2. 去掉纹理，只写 `tid & 1` 与 `tid >> 1` 的探针（纯 buffer，2x2、local 1x1）也只落地
   两组数据，**且写入位置与线程的对应关系在不同网格下不稳定**（4x1 时只有第 3 个槽位
   有值）。
3. 结论：缺陷在**多 invocation 的 thread position 计算或按 invocation 的写回路径**，与
   纹理读取本身无关（buffer-only 探针同样失败）。单 invocation 全链路是正确的。
4. 对照事实：现有 buffer conformance（v7 subset chain、v9 多 command buffer、10x3 grid
   + local 8x2x1 的 `indexed_boundary_dispatch`）**全部通过**，所以这不是通用 dispatch
   缺陷，而是本 fixture 的访问模式触发的（`tid & 1` / `tid >> 1` 这类位运算构造的坐标或
   地址，与现有 fixture 使用的 `getelementptr + tid` 模式不同）。
5. 下一步排查入口（按优先级）：把探针 fixture 的坐标计算换成与 `indexed_boundary`
   相同的模式（直接用 `tid` 作为索引，不做位运算），确认位运算模式是否触发 translator
   的 footprint/地址降级缺陷；若是，补一个 translator 侧的回归用例。

**决定性对照（同日，`af88159`）**：把 fixture 改成与通过用例完全同构的形态（`<3 x i32>`
thread position、workgroup barrier、直接索引），并在**同一执行路径**上跑了已通过的
`copy_3d` buffer kernel（5x3 grid / local 5x1，15 个 invocation 全部正确落地）。结论：

- 执行器、pool key、descriptor、readback、多 invocation dispatch 全部正常；
- **只有"纹理读取 + thread position"组合会丢 invocation**（单 invocation 永远正确）；
- 因此缺陷在 **translator 把 `air.read_texture_2d` 与 thread position builtin 组合降级**
  的路径上；修复应在 pinned metal2vulkan 的纹理 intrinsic 降级或坐标构造处，而不是在
  provider 侧。

**下一步（按优先级）**：

1. 用 `spirv-dis` 对比单 invocation 与多 invocation 两种 dispatch plan 下该 fixture 的
   SPIR-V（重点看 image read 的坐标来源与 `gl_GlobalInvocationID` 的使用），确认是坐标被
   常量折叠还是 invocation 索引丢失；
2. 若确认是 translator 缺陷，最小复现应作为上游 metal2vulkan 的 issue/回归用例提交，并在
   本仓库的 conformance 里保留一个 xfail 记录；
3. 在缺陷修复前，v11 的纹理用例保持单 invocation（已通过），多 invocation 的纹理用例与
   线程组内存/barrier 用例一起延后。

**SPIR-V 级复核（同日，`f683d19`）**：用 `spirv-dis` 逐条核对后，**translator 与 provider
的输入都是正确的**：

- SPIR-V 的线程位置是 `gl_GlobalInvocationID`（Input builtin）加 push constant 里的
  `thread_base`，x/y/z 三个分量都正确提取；坐标计算 `x & 1`、`y & 3`、`cell = (y << 2) + x`
  与 AIR 完全一致；
- pipeline 创建时的工作组尺寸特化正确：`spec_ids=[0,1,2]`、`data=[4,4,1]`（以及 [4,1,1]、
  [1,4,1] 的对应值），dispatch 参数 `local=[4,4,1] groups=[1,1,1] base=[0,0,0]` 正确；
- 但**设备侧实际执行的 `GlobalInvocationID.x` 恒为 0，y 承载线性 invocation 号**：三种
  dispatch（4x4、4x1、1x4）都观察到写入落在 `4*y` 位置（即 x=0），常量写入探针同样如此。

这排除了 provider、translator 与特化的嫌疑，问题在**驱动对 `GlobalInvocationID` 与
特化工作组尺寸的求值**。`METAL_API_DEBUG_DISPATCH=1` 现在可以复现完整输入（pipeline 特化
数据 + dispatch 参数），供下一步对照实验使用。

**下一步（更新）**：

1. 用 `vulkaninfo`/独立最小 SPIR-V 模块（手工编写、不经 translator）在同一 Lavapipe 上验证
   `GlobalInvocationID` 与 spec-constant 工作组尺寸的组合是否按预期工作：
   - 若独立模块也异常 → 驱动（Lavapipe）问题，应改用已确认的行为模式（如显式传入
     `local_size` 参数、或用 `gl_WorkGroupID * gl_WorkGroupSize + gl_LocalInvocationID`
     手工计算），并在 RTX 5060 上复验；
   - 若独立模块正常 → translator 生成的模块与驱动的某个交互问题（如 `OpSpecConstant` 使用
     方式），回到 translator 侧修补。

**驱动行为的细化测量（同日，探针已清理）**：

- 直接输出 `gid.x` 与 `gid.y` 的探针显示：4x4 local 时 `gid.x` **正确**地按
  `[0,1,2,3]` 循环、`gid.y` 取到 0..3；4x1 local 时同样正确；也就是说**两个分量本身没有
  被压平**；
- 但同一探针里"每线程一个工作组"（grid 4x4 / local 1x1，16 个纯单线程组）执行真实纹理
  读取时，输出仍只有 3 个非零值（0、1、1），与逐组执行的预期 `0..15` 相差很远；
- 结论：丢掉 invocation 的不是组件值本身，而是 **多 invocation 写回时的可见性/落地**
  ——同一 command buffer 内 16 个组对同一 storage buffer 的写，只有最后若干次被主机读回
  观测到。这与驱动对 storage buffer 写回可见性的处理有关（无 barrier / 无 memory
  dependency 的多次写回）。

**修正后的下一步**：

1. 在多 invocation 用例的最后一次 dispatch 之后、回读之前，插入一次
   `COMPUTE_SHADER → HOST` 的 memory barrier（我们现在只在整条命令缓冲结束处插了一次），
   验证是否恢复全部写回；
2. 若 barrier 不能解释，再用手工 SPIR-V 模块（不经 translator）在 Lavapipe 上复现同样的
   16 组写入，以区分驱动与模块；
3. 单 invocation 的纹理路径（已通过）足以支撑 v11 的最小纹理用例；多 invocation 的纹理
   用例在本次修正之后再进入 v11。

**屏障实验的结果（同日，代码已回退）**：在每次 dispatch 之后插入
`COMPUTE_SHADER → COMPUTE_SHADER`（SHADER_WRITE → SHADER_READ|WRITE）屏障后，4x4 纹理
用例的输出**完全不变**（仍只有两个非零值），所以问题不是写回可见性。

**当前最强的剩余假设**：多 invocation 下 **`OpImageFetch` 的返回值**，而不是线程位置或
写回。证据链：

- 线程位置的 x/y 分量都被实测为正确（`[0,1,2,3]` × 0..3）；
- 常量写入探针（不经纹理）在多 invocation 下**全部落地**（只有同一格被多线程覆盖时才会
  看似丢失）；
- 真实纹理 fixture 的输出模式（只有 texel x=1 的值出现）说明多数 invocation 读回的是
  **同一个 texel**，而位置与地址计算都已被排除。

**下一步（按优先级）**：

1. 用"每线程读取自己的 texel 并写入自己的格子"的 fixture（去掉 `and 1`/`and 3` 掩码，
   直接 `coord = (x, y)`）在 Lavapipe 上复测：若 16 个 texel 全部正确，则原 fixture 的
   掩码写回模式才是触发点；若仍失败，则确认是 `OpImageFetch` 在多 invocation 下的行为；
2. 在同一位置用手工 SPIR-V（不含 translator）对照，区分驱动与 translator；
3. 单 invocation 纹理路径可继续用于 v11；多 invocation 纹理用例等待上述结论。

**无掩码对照的最终结论（同日，探针已清理）**：用"每线程读自己的 texel（`coord = (x, y)`、
`cell = 4y + x`）"的无掩码 fixture 在三种形态下复测（grid 4x4 / local 1x1、grid 4x4 /
local 4x4、grid 4x1 / local 1x1），输出**永远只有 y=0 行**得到正确值；把坐标换成
`(y, x)` 的转置探针后，输出变成只有 x=0 列有值。两个实验共同证明：

**在这台 Lavapipe 上，`GlobalInvocationID.x` 对所有 invocation 恒为 0**（y 可以变化）。
这与 SPIR-V、特化数据、dispatch 参数全部正确的实测结果矛盾，属于**驱动侧的求值异常**
（`llvmpipe (LLVM 22.1.8)`）。

**下一步（更新，按优先级）**：

1. **先在 RTX 5060 真机上复跑同一个 fixture**（`windows-rtx5060` 路径），确认这是
   Lavapipe 特有还是通用行为——这是本项目"真机 PASS"纪律的应有之义，也是判断是否需要
   向 mesa/Lavapipe 报 bug 的依据；
2. 若 NVIDIA 正常：在 CI 的纹理用例上标注平台差异（Lavapipe 跳过多 invocation 纹理用例、
   真机执行），并在 `docs/16` 记录驱动版本；
3. 若 NVIDIA 同样异常：回到 translator（检查 `metal2vulkan_dispatch_region` 的 push
   constant 布局是否与驱动期望的 `GlobalInvocationID` 计算存在语义冲突），并考虑改用
   显式传入 `local_size` 参数、由内核自行计算 `group_id * local_size + local_id` 的方案。

**RTX 5060 真机复验（同日，临时诊断二进制已删除）**：用同一个 fixture 编译成临时 Windows
二进制并在 RTX 5060 上执行，**同样复现多 invocation 缺陷**，但输出模式与 Lavapipe 不同：

- `GRID=(4,4,1) LOCAL=(4,4,1)` 与 `LOCAL=(1,1,1)` 都得到
  `[0, 1, 0, 1, 8, 9, 8, 9, 0, 0, ...]`（16 词中只有 4 个非零）；
- Lavapipe 得到的是 `[0, 1, 1, 0, 0, ...]` 一类的另一种子集。

不同驱动给出不同子集，说明缺陷**不是驱动特有**，而是我们这一侧的多 invocation 语义在某处
不可移植（translator 生成的坐标/位置组合在真实驱动上同样不能得到 16 个不同结果）。
**修正后的结论**：这不是"Lavapipe 的锅"，下一步应回到 translator/provider 组合，优先验证
§4.3 第 1 项的替代方案——改用显式传入的 `local_size` 与 `group_id`，由内核自行计算全局
坐标（不依赖 `GlobalInvocationID` 在特化工作组尺寸下的求值），并在两个驱动上对照。

**最终定位（同日，又三组对照，探针全部清理）**：

1. **纯 buffer 基线**：完全相同的地址计算（`cell = 4y + x`、`GlobalInvocationID`），
   去掉纹理读取后，4x4/local 4x4 与 4x4/local 1x1 **两种形态都完整落地 `[0..15]`**。
2. **掺杂纹理读取**：同一个内核只把写入值改成 `texel + 100`，输出变成
   `[100,101,102,103,100,100,...]`——**前 4 个线程读到正确的 texel（0..3），其余 12 个
   线程全部读到 texel 0**（即它们的坐标被折叠成 (0,0)）。
3. **显式坐标方案不可用**：改用 `threadgroup_position_in_grid` +
   `thread_position_in_threadgroup` + `threads_per_threadgroup` 手算全局坐标，被本项目的
   footprint 证明拒绝（`buffer 0 has data-dependent or unbounded access`）——translator 的
   地址证明无法表达组/局部运算的组合口径。

**结论**：缺陷是 **translator 在把 `air.read_texture_2d` 与 thread position builtin
组合降级时**，除少量 invocation 外把坐标折叠为 0（不是 `GlobalInvocationID` 本身的求值
问题，纯 buffer 对照已排除）。修复位置应在 pinned metal2vulkan 的纹理 intrinsic 降级路径，
最小复现就是上面第 2 条对照（同一 AIR 只差一次纹理读取）。

**下一步**：把第 2 条对照整理成上游（metal2vulkan）issue 的最小复现与期望行为说明；
在本仓库的 conformance 里保留单 invocation 的纹理用例（已通过），多 invocation 纹理用例
等上游修复后再进入 v11。

## 5. 边界（本文不做）

- 不做 mipmap 生成、多重采样、纹理数组、压缩格式；
