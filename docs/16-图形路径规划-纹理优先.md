# 图形路径规划：从纹理开始（2026-09-13）

> 本文是图形/显示路径的启动规划。当前的 provider 契约、conformance 矩阵与比较器都建立在
> buffer compute 子集上（v1–v10），本文只定义**第一步**与依赖顺序，不改动已通过的契约。
> 相关：`docs/09`（总目标与三道门）、`docs/14`/`docs/15`（range hazard 与共享分配，纹理
> 的 backing 会复用这套语义）、`docs/13`（回收与设备丢失）。

## 1. 为什么要先做纹理

`docs/09` §13.3 把图形路径列为未实现：纹理、render pass、sampler、render pipeline、
presentation、swapchain、heaps、ICB。它们不是并列关系，有依赖序：

```text
纹理资源（创建/写/读/格式） → sampler → 纹理读取的 compute 用例
   → render pipeline（顶点/片元） → render pass 与附件
   → presentation / swapchain → heaps / ICB
```

纹理同时是**唯一一个可以继续用现有 compute 轨道验证**的图形特性：一个 compute kernel
读取 2D 纹理、写入 buffer（或反向），五路径比较器只需在 buffer 之外增加"纹理采样结果"
这一观测面。因此第一步选纹理，而不是 render pass。

## 2. 已经具备的条件（无需重新发明）

pinned 的 metal2vulkan（`43c46ac`）已经为纹理准备好了接口，provider 只需要接上：

- `reflect::ResourceAccess` 已有 `Sampled`（`OpTypeImage Sampled=1`）与 `Storage`
  （`Sampled=2`）两个取值，buffer 访问分类（`Unused/ReadOnly/WriteOnly/ReadWrite`）保持不变；
- `ResourceBinding::texture_shape` 与 `DescriptorLocation`（set/binding/count）描述了纹理的
  descriptor 位置与形状要求；validation 侧的 executor contract 已覆盖
  `texture2d_ms`、`texture_buffer`、`texture2d<uint, write>` 等边界，以及
  `air.sample_texture_*`、`air.gather_texture_2d` 这些 intrinsic 的合法性检查；
- `SynthesizedNullTexture` / `SynthesizedReadSampler` 说明 translator 会在 `air.get_null_texture_2d()`
  与 `air.get_read_sampler()` 处要求 consumer 提供真实 image/sampler——这正是 provider 的
  admission 需要显式支持或拒绝的两类占位资源。

当前阻塞点在 core：`BufferAccess` 只有 buffer 四态，`ValidatedComputeTrace` 的资源池只有
`BufferView`。`Sampled`/`Storage` 目前会被保守地当成可写 buffer 处理（见
`docs/09` 流水线与 `crates/metal-api-vulkan/src/lib.rs` 的访问分类），这在新契约落地前是
**安全但不可用**的。

## 3. 第一步的增量定义（建议）

**目标**：同一个 compute kernel 在五条路径上对同一张 2D 纹理采样，并把结果写入 buffer；
byte 级 parity 由现有比较器扩展到"纹理观测"。

1. **core 契约**（`metal-api-core/src/provider.rs`）
   - 新增 `TextureId`/`TextureView`（type、format、size、mip/array 维度、usage）与
     `TextureResource`（source：owned bytes / staged / borrowed）；
   - `ResourceAccess` 增补 `Sampled`/`Storage` 的稳定映射（不改变 buffer 四态语义）；
   - `ComputeTrace` 的资源池扩展为 buffer + texture，`MAX_SERIAL_RESOURCES` 复用；
   - 与 range hazard 的关系：纹理按"整资源在途"预约起步，subresource 并发留到后续文档。
2. **Vulkan provider**：`Sampled` → `vk::Image`（`VK_IMAGE_TYPE_2D`、线性 tiling、host-visible
   上传一次）；`Storage` → storage image；descriptor 按反射的 set/binding 绑定；采样器用
   pinned translator 的 sampler 描述（nearest/linear + clamp 起步）。
3. **native provider**：`MTLTexture`（`StorageModeShared`，`replaceRegion` 上传，
   `getBytes` 回读）；sampler 状态与 Vulkan 对齐。
4. **conformance v11**：一个新 fixture `sample_texture_2d`（4x4 RGBA8 输入纹理 + 4 字节输出
   buffer），Swift oracle 用 `MTLTexture` + 同样的 MSL 采样；比较器增加纹理观测字段
   （采样结果已经在 buffer 里，所以第一版可以完全复用现有 buffer 比较器——这是选纹理的
   另一个理由）。
5. **验收**：五路径 parity（v1–v10 不变 + v11 通过）；Lavapipe 与 RTX 5060 真机；
   CI 五 job 绿；证据归档。纹理读取的操作计数沿用 `copy_in/copy_out` 的组织方式，
   但需要先定义"纹理的 copy 单位"（建议按 texture resource，不按字节）。

## 4. 开放问题（实现前需要先定）

- `Sampled`/`Storage` 是否进入 `ProviderCapabilities`，还是按现有 `AliasMode` 的方式由
  provider 声明支持面？
- 纹理的"在途"语义：整纹理独占 vs subresource range（与 `docs/14` 的 range hazard 对齐）。
- 格式矩阵：第一版只支持 `RGBA8Unorm`、`R32Uint`、`R32Float` 中哪一个（取决于 `copy_word`
  类 fixture 的最小可行集）。
- `SynthesizedNullTexture`/`SynthesizedReadSampler`：第一版是显式 typed-refuse（推荐），
  还是必须支持（否则某些真实 shader 无法进入）？
- 纹理的 writeback 语义：`Storage` 纹理是否需要与 buffer 相同的字节精确回读。

## 5. 边界（本文不做）

- 不做 render pass、render pipeline、presentation、swapchain、heaps、ICB；
- 不做 mipmap 生成、多重采样、纹理数组、压缩格式；
- 不做 guest memory 的纹理 backing（那是 guest memory 生命周期的下游）；
- 不改动 v1–v10 的既有契约、比较器语义与 provider 能力声明。
